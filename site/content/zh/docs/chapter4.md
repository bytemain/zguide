# 第 4 章 - 可靠的请求 - 回复模式 {#reliable-request-reply}

[第 3 章 - 高级请求 - 回复模式](chapter3#advanced-request-reply) 介绍了 ZeroMQ 请求 - 回复模式的高级用法，并提供了工作示例。本章将探讨可靠性的一般问题，并在 ZeroMQ 核心请求 - 回复模式之上构建一组可靠的消息传递模式。

在本章中，我们重点关注用户空间请求 - 回复*模式*，即可重用的模型，帮助您设计自己的 ZeroMQ 架构：

* **懒惰海盗模式**：客户端侧的可靠请求 - 回复
* **简单海盗模式**：使用负载均衡的可靠请求 - 回复
* **偏执海盗模式**：带心跳的可靠请求 - 回复
* **管家模式**：面向服务的可靠队列
* **泰坦尼克模式**：基于磁盘/断开的可靠队列
* **双星模式**：主备服务器故障转移
* **自由职业者模式**：无代理的可靠请求 - 回复

我们将逐一介绍这些模式，从简单到复杂。

## 什么是"可靠性"？ {#What-is-Reliability}

大多数谈论"可靠性"的人并不知道他们真正的意思。我们只能根据故障来定义可靠性。也就是说，如果我们能够处理一组明确定定和理解的故障，那么我们就对这些故障是可靠的。不多不少。因此，让我们看看在分布式 ZeroMQ 应用程序中可能出现的故障原因，按概率大致降序排列：

* **应用程序代码**是最糟糕的罪魁祸首。它可能崩溃并退出、冻结并停止响应输入、运行太慢无法处理输入、耗尽所有内存等等。

* **系统代码**——比如我们使用 ZeroMQ 编写的代理——可能因与应用程序代码相同的原因而死亡。系统代码*应该*比应用程序代码更可靠，但它仍然可能崩溃和烧毁，特别是如果它试图为慢客户端排队消息而耗尽内存。

* **消息队列**可能溢出，通常发生在学会粗暴处理慢客户端的系统代码中。当队列溢出时，它会开始丢弃消息。因此我们会得到"丢失"的消息。

* **网络**可能失败（例如，WiFi 被关闭或超出范围）。ZeroMQ 在这种情况下会自动重新连接，但在此期间，消息可能会丢失。

* **硬件**可能失败，并带走运行在该机器上的所有进程。

* **网络**可能以奇特的方式失败，例如，交换机上的某些端口可能死亡，网络的这些部分变得无法访问。

* **整个数据中心**可能被闪电、地震、火灾击中，或者更常见的电力或冷却故障。

要使软件系统对*所有*这些可能的故障都完全可靠是一项极其困难和昂贵的工作，超出了本书的范围。

因为上述列表中的前五种情况涵盖了 99.9% 的现实世界需求（根据我刚刚进行的一项高度科学研究，该研究还告诉我 78% 的统计数据是当场编造的，而且永远不要相信我们没有自己伪造的统计数据），这就是我们要研究的内容。如果您是一家大公司，有钱花在最后两种情况上，请立即联系我的公司！我海滩房子后面有一个大洞，等着变成高管游泳池。

## 设计可靠性 {#Designing-Reliability}

因此，为了把事情变得极其简单，可靠性就是"当代码冻结或崩溃时保持正常工作"，这种情况我们简称为"死亡"。然而，我们想要保持正常工作的不仅仅是消息。我们需要考虑每个核心 ZeroMQ 消息模式，看看如何使其在代码死亡时也能工作（如果我们能做到的话）。

让我们逐一来看：

* **请求 - 回复**：如果服务器死亡（在处理请求时），客户端可以弄清楚这一点，因为它不会得到回复。然后它可以发脾气放弃、等待稍后重试、找到另一个服务器等等。至于客户端死亡，我们现在可以将其视为"别人的问题"。

* **发布 - 订阅**：如果客户端死亡（已经获取了一些数据），服务器并不知道。发布 - 订阅不会从客户端向服务器发送任何信息。但客户端可以通过带外方式联系服务器，例如通过请求 - 回复，并询问"请重新发送我错过的所有内容"。至于服务器死亡，这超出了我们这里的范围。订阅者也可以自我验证它们运行得不是太慢，并在运行太慢时采取行动（例如，警告操作员并死亡）。

* **管道**：如果工人死亡（在处理任务时），上游节点可以弄清楚这一点，因为它不会得到确认。上游节点可以放弃并等待稍后重试、找到另一个工人等等。至于上游节点死亡，我们可以将其视为"别人的问题"。

基本的请求 - 回复模式（REQ 客户端套接字对 REP 服务器套接字进行阻塞发送/接收）在处理最常见的故障类型方面得分很低。如果服务器在处理请求时崩溃，客户端将永远挂起。如果网络丢失了请求或回复，客户端将永远挂起。

请求 - 回复仍然比 TCP 好得多，这要归功于 ZeroMQ 能够静默地重新连接对等方、负载均衡消息等能力。但它仍然不足以用于实际工作。你唯一可以真正信任基本请求 - 回复模式的情况是在同一进程中的两个线程之间，那里没有网络或单独的服务器进程会死亡。

然而，通过一点额外的工作，这个谦逊的模式可以成为跨分布式网络进行实际工作的良好基础，我们得到一组可靠的请求 - 回复（RRR）模式，我喜欢称之为//海盗//模式（你最终会明白这个笑话，我希望）。

根据我的经验，大致有三种方式将客户端连接到服务器。每种都需要特定的可靠性方法：

* **多个客户端直接对话单个服务器**。用例：单个众所周知的服务器，客户端需要与之对话。我们旨在处理的故障类型：服务器崩溃和重启，以及网络断开。

* **多个客户端对话代理代理，该代理将工作分配给多个工人**。用例：面向服务的交易处理。我们旨在处理的故障类型：工人崩溃和重启、工人忙循环、工人过载、队列崩溃和重启，以及网络断开。

* **多个客户端对话多个服务器，没有中介代理**。用例：分布式服务，如名称解析。我们旨在处理的故障类型：服务崩溃和重启、服务忙循环、服务过载，以及网络断开。

这些方法各有权衡，通常你会混合使用它们。我们将详细研究所有三种方法。

仅在客户端处理故障适用于我们有一组客户端对话单个服务器的情况。它可以处理服务器崩溃，但只有当恢复意味着重启相同的服务器时。如果存在永久性错误，例如服务器硬件上的电源故障，这种方法将不起作用。因为服务器中的应用程序代码通常是任何架构中故障的最大来源，依赖单个服务器不是一个好主意。

所以，优点和缺点：

* 优点：简单易懂和实现。
* 优点：易于与现有的客户端和服务器应用程序代码配合使用。
* 优点：ZeroMQ 会自动重试实际的重新连接，直到它工作。
* 缺点：不会故障转移到备份或备用服务器。

## 基本可靠队列（简单海盗模式） {#Basic-Reliable-Queuing-Simple-Pirate-Pattern}

懒惰海盗模式适用于单个客户端 - 服务器对。但如果我们有多个客户端和多个服务器呢？我们需要一个代理来分配工作。让我们看看如何使代理可靠。

简单海盗模式使用一个代理来分配工作给多个工人。代理检测死亡的工人，并将工作重新分配给其他工人。

这是简单海盗模式的架构：

{{< textdiagram name="fig47.png" figno="47" title="Simple Pirate Pattern" >}}
     .---------.      .---------.      .---------
     |  Client |      |  Broker |      |  Worker |
     |   REQ   |      |  ROUTER |      |   REQ   |
     '----+----'      +----+----+      '----+----'
          |              |  |              |
          '--------------+--+--------------'
                         |  |
                         v  v
{{< /textdiagram >}}

简单海盗模式的关键是：

* 工人定期向代理发送心跳。
* 代理跟踪工人的心跳。
* 如果代理在一定时间内没有从工人那里收到心跳，它会认为工人死亡。
* 代理将死亡工人的工作重新分配给其他工人。

队列代理的基础是高级请求 - 回复中的负载均衡代理。处理死亡或阻塞的工人所需的//最少//工作是什么？结果证明，这 surprisingly 很少。我们已经在客户端有了重试机制。因此，使用负载均衡模式会工作得很好。这符合 ZeroMQ 的理念，即我们可以通过在中間插入天真的代理来扩展点对点模式，如请求 - 回复。

## 健壮的可靠队列（偏执海盗模式） {#Robust-Reliable-Queuing-Paranoid-Pirate-Pattern}

偏执海盗模式是简单海盗模式的扩展，它增加了更复杂的心跳和重试逻辑。这个模式更健壮，可以处理更多的故障情况。

偏执海盗模式的关键是：

* 工人定期向代理发送心跳。
* 代理跟踪工人的心跳。
* 客户端定期向代理发送心跳。
* 代理跟踪客户端的心跳。
* 如果代理在一定时间内没有从工人或客户端那里收到心跳，它会认为它们死亡。
* 代理将死亡工人的工作重新分配给其他工人。
* 客户端可以重试失败的请求。

简单海盗队列模式工作得相当好，特别是因为它只是两个现有模式的组合。不过，它确实有一些弱点：

* 它在面对队列崩溃和重启时不够健壮。客户端会恢复，但工人不会。虽然 ZeroMQ 会自动重新连接工人的套接字，但就新启动的队列而言，工人还没有发出就绪信号，因此不存在。为了解决这个问题，我们必须从队列到工人进行心跳检测，这样工人就可以检测到队列何时消失。

* 队列不检测工人故障，因此如果工人在空闲时死亡，队列无法将其从工人队列中移除，直到队列向它发送请求。客户端等待并重试是徒劳的。这不是一个关键问题，但这不是好事。为了使这正常工作，我们从工人到队列进行心跳检测，这样队列就可以在任何阶段检测丢失的工人。

我们将在一个适当迂腐的偏执海盗模式中修复这些问题。

我们之前为工人使用了 REQ 套接字。对于偏执海盗工人，我们将切换到 DEALER 套接字。这具有让我们随时发送和接收消息的优势，而不是 REQ 强加的锁定步骤发送/接收。DEALER 的缺点是我们必须自己做信封管理（重新阅读高级请求 - 回复以了解这个概念）。

## 心跳 {#Heartbeating}

心跳解决了知道对等方是活着还是死了的问题。这不是 ZeroMQ 特有的问题。TCP 有一个很长的超时（大约 30 分钟），这意味着可能无法知道对等方是否已经死亡、断开连接，或者带着一箱伏特加、一个红发女郎和一个大额费用账户去布拉格度周末了。

正确实现心跳并不容易。在编写偏执海盗示例时，大约花了五个小时才让心跳正常工作。请求 - 回复链的其余部分可能只花了十分钟。尤其容易创建"假故障"，即对等方决定它们已断开连接，因为心跳没有正确发送。

我们将看看人们用于 ZeroMQ 心跳的三种主要答案。

### 忽略它

最常见的方法是完全不做心跳，希望最好的结果。许多（如果不是大多数）ZeroMQ 应用程序都这样做。ZeroMQ 通过在许多情况下隐藏对等方来鼓励这一点。这种方法会导致什么问题？

* 当我们在跟踪对等方的应用程序中使用 ROUTER 套接字时，随着对等方断开连接和重新连接，应用程序会泄漏内存（应用程序为每个对等方持有的资源）并变得越来越慢。

* 当我们使用基于 SUB 或 DEALER 的数据接收方时，我们无法区分好的沉默（没有数据）和坏的沉默（另一端死亡）。当接收方知道另一端死亡时，它可以例如切换到备份路由。

* 如果我们使用长时间保持沉默的 TCP 连接，在某些网络中，它只会死亡。发送一些东西（技术上，"保持活动"多于心跳），将使网络保持活动。

### 单向心跳

第二个选项是从每个节点向其对等方每秒左右发送一次心跳消息。当一个节点在几秒钟内没有听到另一个节点的消息时，它会将该对等方视为死亡。听起来不错，对吧？可悲的是，不。这在某些情况下有效，但在其他情况下有讨厌的边界情况。

对于发布 - 订阅，这确实有效，它是你可以使用的唯一模型。SUB 套接字无法与 PUB 套接字对话，但 PUB 套接字可以愉快地向其订阅者发送"我还活着"消息。

作为优化，你可以仅在没有真实数据要发送时发送心跳。此外，如果网络活动是一个问题（例如，在移动网络上，活动会耗尽电池），你可以逐渐减慢发送心跳的速度。只要接收方可以检测到故障（活动的急剧停止），那就很好。

这种设计的典型问题是：

* 当我们发送大量数据时，它可能不准确，因为心跳会延迟在这些数据后面。如果心跳被延迟，你可能会因网络拥塞而得到虚假的超时和断开连接。因此，始终将//任何//传入数据视为心跳，无论发送方是否优化掉心跳。

* 虽然发布 - 订阅模式会为消失的目的地删除消息，但 PUSH 和 DEALER 套接字会将它们排队。因此，如果你向一个死亡的对等方发送心跳，然后它又回来了，它会得到你发送的所有心跳，这可能是数千个。哇，哇！

* 这种设计假设整个网络的心跳超时是相同的。但这不会准确。一些对等方会希望非常积极的心跳，以便快速检测故障。而另一些对等方会希望非常放松的心跳，以便让沉睡的网络保持睡眠状态并节省电力。

### Ping-Pong 心跳

第三个选项是使用 ping-pong 对话。一个对等方向另一个对等方发送 ping 命令，后者用 pong 命令回复。两个命令都没有任何有效载荷。ping 和 pong 不相关。因为在某些网络中，"客户端"和"服务器"的角色是任意的，我们通常指定任何对等方实际上都可以发送 ping 并期望收到 pong 回复。然而，由于超时取决于动态客户端最了解的网络拓扑，通常是客户端 ping 服务器。

这适用于所有基于 ROUTER 的代理。我们在第二个模型中使用的相同优化使这个工作得更好：将任何传入数据视为 pong，并且仅在不发送其他数据时发送 ping。

### 偏执海盗的心跳

对于偏执海盗，我们选择了第二种方法。今天可能不是最简单的选择：如果今天设计这个，我可能会尝试 ping-pong 方法。然而，原理是相似的。心跳消息在两个方向上异步流动，任何对等方都可以决定另一个是"死亡"的，并停止与它对话。

在工人中，这是我们处理来自队列的心跳的方式：

* 我们计算一个//活跃度//，这是我们在决定队列死亡之前仍然可以错过的心跳数。它从三开始，每次错过心跳时我们都会递减。
* 我们在 {{zmq_poll}} 循环中等待，每次等待一秒钟，这是我们的心跳间隔。
* 如果在此期间有来自队列的任何消息，我们会将活跃度重置为三。
* 如果在此期间没有消息，我们会倒数活跃度。
* 如果活跃度达到零，我们认为队列死亡。
* 如果队列死亡，我们会销毁套接字，创建一个新套接字，并重新连接。
* 为了避免打开和关闭太多套接字，我们会在重新连接前等待某个间隔，并且每次将间隔加倍，直到达到 32 秒。

这是我们处理//向//队列发送心跳的方式：

* 我们计算何时发送下一个心跳；这是一个单一变量，因为我们正在与一个对等方，即队列对话。
* 在 {{zmq_poll}} 循环中，每当我们经过这个时间，我们就会向队列发送心跳。

以下是工人的基本心跳代码：

```c
#define HEARTBEAT_LIVENESS  3       //  3-5 is reasonable
#define HEARTBEAT_INTERVAL  1000    //  msecs
#define INTERVAL_INIT       1000    //  Initial reconnect
#define INTERVAL_MAX       32000    //  After exponential backoff

...
//  If liveness hits zero, queue is considered disconnected
size_t liveness = HEARTBEAT_LIVENESS;
size_t interval = INTERVAL_INIT;

//  Send out heartbeats at regular intervals
uint64_t heartbeat_at = zclock_time () + HEARTBEAT_INTERVAL;

while (true) {
    zmq_pollitem_t items [] = { { worker,  0, ZMQ_POLLIN, 0 } };
    int rc = zmq_poll (items, 1, HEARTBEAT_INTERVAL * ZMQ_POLL_MSEC);

    if (items [0].revents & ZMQ_POLLIN) {
        //  Receive any message from queue
        liveness = HEARTBEAT_LIVENESS;
        interval = INTERVAL_INIT;
    }
    else
    if (--liveness == 0) {
        zclock_sleep (interval);
        if (interval < INTERVAL_MAX)
            interval *= 2;
        zsocket_destroy (ctx, worker);
        ...
        liveness = HEARTBEAT_LIVENESS;
    }
    //  Send heartbeat to queue if it's time
    if (zclock_time () > heartbeat_at) {
        heartbeat_at = zclock_time () + HEARTBEAT_INTERVAL;
        //  Send heartbeat message to queue
    }
}
```

队列做同样的事情，但管理每个工人的到期时间。

以下是您自己心跳实现的一些提示：

* 使用 {{zmq_poll}} 或反应器作为应用程序主要任务的核心。

* 首先建立对等方之间的心跳，通过模拟故障进行测试，//然后//构建其余的消息流。之后添加心跳要棘手得多。

* 使用简单的跟踪，即打印到控制台，来完成这项工作。为了帮助您跟踪对等方之间的消息流，使用 zmsg 提供的转储方法，并递增地为您的消息编号，这样您就可以看到是否有间隙。

* 在实际应用程序中，心跳必须是可配置的，并且通常与对等方协商。一些对等方会希望积极的心跳，低至 10 毫秒。其他对等方会相距甚远，并希望心跳高达 30 秒。

* 如果您为不同的对等方有不同的心跳间隔，您的轮询超时应该是这些中的最低（最短）时间。不要使用无限超时。

* 在您用于消息的同一套接字上进行心跳检测，这样您的心跳也充当//保持活动//，以防止网络连接变得陈旧（某些防火墙可能对沉默连接不友好）。

## 契约和协议 {#Contracts-and-Protocols}

如果您注意的话，您会意识到偏执海盗与简单海盗不互操作，因为心跳。但我们如何定义"互操作性"呢？为了保证互操作性，我们需要一种契约，一种让不同时间和地点的不同团队编写保证一起工作的代码的协议。我们称这为"协议"。

在没有规范的情况下进行实验很有趣，但这并不是真正应用程序的明智基础。如果我们想用另一种语言编写工人会发生什么？我们是否必须阅读代码才能了解事情是如何工作的？如果我们想出于某种原因更改协议会发生什么？即使是一个简单的协议，如果它成功，也会发展并变得更加复杂。

缺乏契约是可丢弃应用程序的确定迹象。因此，让我们为这个协议写一个契约。我们该怎么做？

在 [http://rfc.zeromq.org rfc.zeromq.org] 有一个 wiki，我们专门将其作为公共 ZeroMQ 契约的主页。
要创建新规范，如果需要，请在 wiki 上注册，并按照说明操作。这相当简单，尽管编写技术文本并不是每个人的茶。

我花了大约十五分钟起草新的 [http://rfc.zeromq.org/spec:6 海盗模式协议]。这不是一个大规范，但它确实足以作为争论的基础（"你的队列不兼容 PPP；请修复它！"）。

将 PPP 变成真正的协议需要更多工作：

* READY 命令中应该有一个协议版本号，以便可以区分 PPP 的不同版本。

* 现在，READY 和 HEARTBEAT 并不完全不同于请求和回复。为了使它们不同，我们需要一个包含"消息类型"部分的消息结构。

## 面向服务的可靠队列（管家模式） {#Service-Oriented-Reliable-Queuing-Majordomo-Pattern}

进步的好的事情是，当律师和委员会不参与时，进展会有多快。[http://rfc.zeromq.org/spec:7 单页 MDP 规范] 将 PPP 变成了更可靠的东西。这就是我们设计复杂架构的方式：首先写下契约，//然后//编写软件来实现它们。

管家协议（MDP）以一种有趣的方式扩展和改进 PPP：它向客户端发送的请求添加了一个"服务名称"，并要求工人注册特定服务。添加服务名称将我们的偏执海盗队列变成了面向服务的代理。MDP 的好处是它来自工作代码、更简单的祖先协议（PPP）和一组精确的改进，每个改进都解决了一个明确的问题。这使得起草变得容易。

要实现管家，我们需要为客户端和工人编写一个框架。要求每个应用程序开发人员阅读规范并使其工作真的不合理，当他们可以使用更简单的 API 来完成工作时。

因此，虽然我们的第一个契约（MDP 本身）定义了我们分布式架构的各个部分如何相互对话，但我们的第二个契约定义了用户应用程序如何与我们即将设计的技术框架对话。

管家有两半，客户端和工人。因为我们将编写客户端和工人应用程序，所以我们需要两个 API。以下是客户端 API 的草图，使用简单的面向对象方法：

```c
mdcli_t *mdcli_new     (char *broker);
void     mdcli_destroy (mdcli_t **self_p);
zmsg_t  *mdcli_send    (mdcli_t *self, char *service, zmsg_t **request_p);
```

就是这样。我们打开与代理的会话，发送请求消息，取回回复消息，并最终关闭连接。以下是工人 API 的草图：

```c
mdwrk_t *mdwrk_new     (char *broker,char *service);
void     mdwrk_destroy (mdwrk_t **self_p);
zmsg_t  *mdwrk_recv    (mdwrk_t *self, zmsg_t *reply);
```

它或多或少是对称的，但工人对话框略有不同。工人第一次执行 recv() 时，它会传递一个空回复。此后，它传递当前回复，并获得一个新请求。

* API 是单线程的。这意味着，例如，工人不会在后台发送心跳。幸运的是，这正是我们想要的：如果工人应用程序卡住，心跳将停止，代理将停止向工人发送请求。

* 工人 API 不进行指数退避；这不值得额外的复杂性。

* API 不做任何错误报告。如果事情不像预期的那样，它们会引发断言（或异常，取决于语言）。这对于参考实现来说是理想的，因此任何协议错误都会立即显示。对于真正的应用程序，API 应该对无效消息具有健壮性。

您可能想知道为什么工人 API 手动关闭其套接字并打开一个新套接字，而当对等方消失并重新出现时，ZeroMQ 会自动重新连接套接字。回顾简单海盗和偏执海盗工人以理解。虽然 ZeroMQ 会在代理死亡并重新启动时自动重新连接工人，但这不足以让工人重新向代理注册。我知道至少有两个解决方案。我们在这里使用的最简单的方法是工人使用心跳监控连接，如果它决定代理死亡，就关闭其套接字并重新开始使用新套接字。另一种方法是代理在从工人那里获得心跳时挑战未知工人，并要求它们重新注册。这需要协议支持。

现在让我们设计管家代理。其核心结构是每个服务一组队列，我们将随着工人的出现创建这些队列（我们可以在工人消失时删除它们，但现在忘记这一点，因为它变得复杂）。此外，我们为每个服务保留一个工人队列。

## 异步管家模式 {#Asynchronous-Majordomo-Pattern}

前一节中的管家实现简单且愚蠢。客户端只是原始的简单海盗，包装在一个性感的 API 中。当我在测试盒上启动客户端、代理和工人时，它可以在大约 14 秒内处理 100,000 个请求。这部分是由于代码，它愉快地复制消息帧，就好像 CPU 周期是免费的一样。但真正的问题是我们正在进行网络往返。ZeroMQ 禁用 [http://en.wikipedia.org/wiki/Nagles_algorithm Nagle 算法]，但往返仍然很慢。

理论在理论上很棒，但在实践中，实践更好。让我们用一个简单的测试程序测量往返的实际成本。这发送了一堆消息，首先等待每条消息的回复，其次作为一批，读取所有回复作为一批。两种方法做相同的工作，但它们给出非常不同的结果。我们模拟客户端、代理和工人：

请注意，客户端线程在开始之前会暂停一小段时间。这是为了解决路由器套接字的一个"特性"：如果你向一个尚未连接的对等方发送消息，消息会被丢弃。在这个例子中，我们不使用负载均衡机制，因此如果没有睡眠，如果工人线程连接太慢，它会丢失消息，使我们的测试变得一团糟。

正如我们所见，在最简单的情况下，往返比异步的"尽可能快地将其推入管道"方法慢 20 倍。让我们看看是否可以将其应用于管家以使其更快。

首先，我们修改客户端 API，将其拆分为两个单独的方法：

```c

void     mdcli_destroy (mdcli_t **self_p);
int      mdcli_send    (mdcli_t *self, char *service, zmsg_t **request_p);
zmsg_t  *mdcli_recv    (mdcli_t *self);
```

不同之处在于：

* 我们使用 DEALER 套接字而不是 REQ，所以我们用一个空的分隔符帧在每个请求和每个响应之前来模拟 REQ。
* 我们不重试请求；如果应用程序需要重试，它可以自己完成。
* 我们将同步的 {{send}} 方法拆分为单独的 {{send}} 和 {{recv}} 方法。
* {{send}} 方法是异步的，在发送后立即返回。因此，调用者可以在获得响应之前发送多条消息。
* {{recv}} 方法等待（有超时）一个响应并将其返回给调用者。

然而，异步管家模式并不全是玫瑰。它有一个根本性的弱点，即如果没有更多的工作，它无法在代理崩溃中幸存。如果你查看 {{mdcliapi2}} 代码，你会看到它在失败后不会尝试重新连接。正确的重新连接需要以下内容：

* 每个请求都有一个编号，每个回复都有一个匹配的编号，这理想情况下需要对协议进行更改以强制执行。
* 在客户端 API 中跟踪和保留所有未完成的请求，即那些尚未收到回复的请求。
* 在故障转移的情况下，客户端 API 需要//重新发送//所有未完成的请求给代理。

这不是一个破坏交易的因素，但它确实表明性能通常意味着复杂性。这对管家来说值得做吗？这取决于您的用例。对于您每个会话调用一次的名称查找服务，不需要。对于为数千个客户端提供服务的 Web 前端，可能需要。

## 服务发现 {#Service-Discovery}

因此，我们有一个很好的面向服务的代理，但我们没有办法知道特定服务是否可用。我们知道请求是否失败，但我们不知道为什么。能够询问代理"回显服务是否正在运行？"是最明显的方法。最显而易见的方法是修改我们的 MDP/客户端协议以添加命令来询问这一点。但 MDP/客户端具有简单的巨大魅力。向它添加服务发现会使它与 MDP/工人协议一样复杂。

另一个选择是做电子邮件所做的事情，并要求无法投递的请求被退回。这在异步世界中可以很好地工作，但它也增加了复杂性。我们需要方法来区分退回的请求和回复，并正确处理这些。

让我们尝试使用我们已经构建的东西，在 MDP 之上构建，而不是修改它。服务发现本身就是一种服务。它实际上可能是几个管理服务之一，例如"禁用服务 X"，"提供统计信息"等。我们想要的是一个通用的、可扩展的解决方案，它不会影响协议或现有应用程序。

因此，这里有一个小 RFC，它在 MDP 之上分层：[http://rfc.zeromq.org/spec:8 管家管理接口 (MMI)]。我们已经在代理中实现了它，尽管除非你阅读了整件事，否则你可能错过了这一点。我将解释它在代理中的工作原理：

* 当客户端请求以 {{mmi.}} 开头的服务时，我们不会将其路由给工人，而是在内部处理它。

* 我们在这个代理中只处理一个服务，即 {{mmi.service}}，服务发现服务。

* 请求的有效载荷是外部服务（由工人提供的真实服务）的名称。

* 代理返回"200"（OK）或"404"（未找到），取决于是否有工人注册该服务。

## 幂等服务 {#Idempotent-Services}

幂等性不是你可以吃药的东西。这意味着可以安全地重复操作。检查时钟是幂等的。把信用卡借给自己的孩子则不是。虽然许多客户端到服务器的用例是幂等的，但有些不是。幂等用例的示例包括：

* 无状态任务分配，即服务器是无状态工人的管道，仅基于请求提供的状态计算回复。在这种情况下，多次执行相同的请求是安全的（尽管效率低下）。

* 将逻辑地址转换为要绑定或连接的端点的名称服务。在这种情况下，多次进行相同的查找请求是安全的。

以下是非幂等用例的示例：

* 日志记录服务。一个人不希望相同的日志信息被记录多次。

* 任何对下游节点有影响的服务，例如，将信息发送给其他节点。如果该服务获得相同的请求多次，下游节点将获得重复的信息。

* 任何以某种非幂等方式修改共享数据的服务；例如，借记银行账户的服务在没有额外工作的情况下不是幂等的。

当我们的服务器应用程序不是幂等的时，我们必须更仔细地考虑它们何时可能崩溃。如果应用程序在空闲时死亡，或者在处理请求时死亡，这通常是可以的。我们可以使用数据库事务来确保借记和贷记始终一起完成，如果要做的话。如果服务器在发送回复时死亡，这是一个问题，因为就它而言，它已经完成了工作。

如果网络在回复返回客户端时死亡，同样的问题也会出现。客户端会认为服务器已经死亡，并重新发送请求，服务器会做两次相同的工作，这不是我们想要的。

为了处理非幂等操作，使用相当标准的解决方案来检测和拒绝重复请求。这意味着：

* 客户端必须用唯一的客户端标识符和唯一的消息编号标记每个请求。

* 服务器在发送回复之前，使用客户端 ID 和消息编号的组合作为键来存储它。

* 当服务器从给定客户端获得请求时，它首先检查它是否有该客户端 ID 和消息编号的回复。如果有，它不会处理请求，而只是重新发送回复。

## 断开连接的可靠性（泰坦尼克模式） {#Disconnected-Reliability-Titanic-Pattern}

一旦您意识到管家是一个"可靠"的消息代理，您可能会想添加一些旋转铁锈（即基于铁的硬盘盘片）。毕竟，这对所有企业消息传递系统都有效。这是一个如此诱人的想法，以至于不得不对它持否定态度有点悲哀。但残酷的愤世嫉俗是我的专长之一。因此，您不希望基于铁锈的代理位于架构中心的一些原因：

* 正如您所看到的，懒惰海盗客户端的表现出奇地好。它适用于从直接客户端到服务器到分布式队列代理的整个架构范围。它确实倾向于假设工人是无状态和幂等的。但我们可以解决这个限制，而不必求助于铁锈。

* 铁锈带来了一整套问题，从性能缓慢到您必须管理、修复和处理的额外部分，因为它们不可避免地会在每天凌晨 6 点出现故障。海盗模式的普遍魅力在于它们的简单性。它们不会崩溃。如果您仍然担心硬件，您可以转向根本没有代理的点对点模式。我将在本章后面解释。

话虽如此，然而，基于铁锈的可靠性有一个合理的用例，即异步断开连接的网络。它解决了海盗的一个主要问题，即客户端必须实时等待答案。如果客户端和工人只是零星连接（将电子邮件视为类比），我们不能在客户端和工人之间使用无状态网络。我们必须在中间放置状态。

因此，这是泰坦尼克模式，我们将消息写入磁盘以确保它们永远不会丢失，无论客户端和工人连接得多么零星。正如我们对服务发现所做的那样，我们将在 MDP 之上分层泰坦尼克，而不是扩展它。这是非常懒惰的，因为这意味着我们可以在专门的工人中实现我们的即发即弃可靠性，而不是在代理中。这有几个原因：

* 它//更容易//，因为我们分而治之：代理处理消息路由，工人处理可靠性。
* 它让我们可以用一种语言编写的代理与用另一种语言编写的工人混合使用。
* 它让我们可以独立发展即发即弃技术。

唯一的缺点是代理和硬盘之间有一个额外的网络跳。好处很容易值得。

有许多方法可以制作持久的请求 - 回复架构。我们将瞄准一个简单无痛的方法。我在玩这个几个小时后能想到的最简单的设计是一个"代理服务"。也就是说，泰坦尼克根本不影响工人。如果客户端想要立即得到回复，它会直接与服务对话，并希望服务可用。如果客户端愿意等待一段时间，它会与泰坦尼克对话，然后问："嘿，伙计，我去买杂货的时候，你能帮我照顾一下这个吗？"

泰坦尼克既是工人又是客户端。客户端和泰坦尼克之间的对话如下：

* 客户端：请帮我接受这个请求。泰坦尼克：好的，完成了。
* 客户端：你有我的回复吗？泰坦尼克：是的，给你。或者，不，还没有。
* 客户端：好的，你现在可以删除那个请求了，我很满意。泰坦尼克：好的，完成了。

而泰坦尼克与代理和工人之间的对话如下：

* 泰坦尼克：嘿，代理，有咖啡服务吗？代理：嗯，是的，看起来有。
* 泰坦尼克：嘿，咖啡服务，请帮我处理一下这个。
* 咖啡：当然，给你。
* 泰坦尼克：太棒了！

您可以解决这个问题以及可能的故障情况。如果工人在处理请求时崩溃，泰坦尼克会无限期重试。如果回复在某个地方丢失了，泰坦尼克会重试。如果请求已处理但客户端没有得到回复，它会再次询问。如果泰坦尼克在处理请求或回复时崩溃，客户端会再次尝试。只要请求完全提交到安全存储，工作就不会丢失。

握手是迂腐的，但可以流水线化，即客户端可以使用异步管家模式做大量工作，然后再获得响应。

我们需要某种方式让客户端请求//其//回复。我们将有许多客户端请求相同的服务，客户端会消失并重新出现不同的身份。以下是一个简单、相当安全的解决方案：

* 每个请求都会生成一个通用唯一 ID（UUID），泰坦尼克在排队请求后将其返回给客户端。
* 当客户端询问回复时，它必须指定原始请求的 UUID。

在现实情况下，客户端会希望安全地存储其请求 UUID，例如在本地数据库中。

在我们跳出去编写另一个正式规范（有趣，有趣！）之前，让我们考虑一下客户端如何与泰坦尼克对话。一种方法是使用单一服务并向其发送三种不同的请求类型。另一种方法，看起来更简单的，是使用三种服务：

* {{titanic.request}}：存储请求消息，并返回请求的 UUID。
* {{titanic.reply}}：获取给定请求 UUID 的回复，如果可用。
* {{titanic.close}}：确认回复已存储和处理。

我们将只做一个多线程工人，正如我们从 ZeroMQ 的多线程经验中看到的那样，这是微不足道的。然而，让我们首先用 ZeroMQ 消息和帧来描绘泰坦尼克的样子。这给了我们 [http://rfc.zeromq.org/spec:9 泰坦尼克服务协议 (TSP)]。

* 使用单个磁盘文件存储所有数据，而不是多个文件。操作系统通常更擅长处理一些大文件，而不是许多小文件。
* 将该磁盘文件组织为循环缓冲区，以便可以连续写入新请求（偶尔进行回绕）。一个线程，以全速写入磁盘文件，可以快速工作。
* 将索引保存在内存中，并在启动时从磁盘缓冲区重建索引。这节省了保持索引完全安全在磁盘上所需的额外磁盘头部颤动。您会希望在每条消息后或每 N 毫秒进行一次 fsync，如果您准备在系统故障情况下丢失最后的 M 条消息。
* 使用固态驱动器而不是旋转氧化铁盘片。
* 预分配整个文件，或者大块分配，允许循环缓冲区根据需要增长和收缩。这避免了碎片，并确保大多数读取和写入是连续的。

等等。我不会推荐的是将消息存储在数据库中，甚至不是"快速"的键/值存储，除非您真的喜欢特定的数据库，并且没有性能担忧。您将为抽象付出高昂的代价，比原始磁盘文件高出 10 到 1000 倍。

如果您想让泰坦尼克//更可靠//，将请求复制到第二个服务器，您会将其放在第二个位置，刚好足够远，以在您对主要位置的核攻击中幸存下来，但又不会太远，以至于您获得太多延迟。

如果您想让泰坦尼克//更快且不那么可靠//，将请求和回复纯粹存储在内存中。这将为您提供断开连接网络的功能，但请求不会在泰坦尼克服务器本身崩溃中幸存下来。

## 高可用性对（双星模式） {#High-Availability-Pair-Binary-Star-Pattern}

双星模式将两个服务器放在主备高可用性对中。在任何给定时间，其中一个（活动的）接受来自客户端应用程序的连接。另一个（被动的）什么也不做，但两个服务器相互监控。如果活动的从网络中消失，在一定时间后，被动的将接管为活动的。

我们在 iMatix 为我们的 [http://www.openamq.org OpenAMQ 服务器] 开发了双星模式。我们设计它：

* 提供一个简单明了的高可用性解决方案。
* 足够简单，可以实际理解和使用。
* 在需要时可靠地进行故障转移，并且仅在需要时。

假设我们有一个运行的双星对，以下是会导致故障转移的不同场景：

* 运行主服务器的硬件出现致命问题（电源爆炸、机器着火，或者有人简单地拔掉了插头），并消失。应用程序看到这一点，并重新连接到备份服务器。
* 主服务器所在的网络段崩溃 - 也许路由器被电源尖峰击中 - 应用程序开始重新连接到备份服务器。
* 主服务器崩溃或被操作员杀死，并且不会自动重启。

故障转移恢复的工作方式如下：

* 操作员重启主服务器并修复导致其从网络中消失的任何问题。
* 操作员在会造成最小破坏的时刻停止备份服务器。
* 当应用程序重新连接到主服务器时，操作员重启备份服务器。

恢复（使用主服务器作为活动的）是手动操作。痛苦的经验告诉我们，自动恢复是不可取的。有几个原因：

* 故障转移会造成对应用程序的服务中断，可能持续 10-30 秒。如果存在真正的紧急情况，这比完全中断要好得多。但如果恢复会造成进一步的 10-30 秒中断，最好在用户离开网络的非高峰时段进行。

* 当出现紧急情况时，绝对的首要任务是为那些试图修复问题的人提供确定性。自动恢复会为系统管理员创造不确定性，他们不再能够确定哪个服务器处于控制状态，而无需仔细检查。

* 自动恢复可能会产生网络故障转移然后恢复的情况，使操作员处于分析所发生情况的困难位置。存在服务中断，但原因不清楚。

话虽如此，双星模式会在主服务器再次运行且备份服务器出现故障时，故障回复到主服务器。事实上，这就是我们触发恢复的方式。

双星对的关闭过程是：

1. 停止被动服务器，然后在任何稍后的时间停止活动服务器，或者
2. 以任何顺序停止两个服务器，但在几秒钟内完成。

以超过故障转移超时时间的任何延迟停止活动服务器，然后停止被动服务器会导致应用程序断开连接，然后重新连接，然后再次断开连接，这可能会干扰用户。

### 详细要求

双星模式尽可能简单，同时仍能准确工作。事实上，当前的设计是第三个完整的设计。我们发现之前的每个设计都太复杂，试图做太多事情，我们剥离功能，直到我们得到一个可以理解、易于使用且足够可靠以值得使用的设计。

这些是我们对高可用性架构的要求：

* 故障转移旨在提供灾难性系统故障的保险，例如硬件故障、火灾、事故等。有更简单的方法可以从普通服务器崩溃中恢复，我们已经介绍了这些方法。

* 故障转移时间应少于 60 秒，最好少于 10 秒。

* 故障转移必须自动发生，而恢复必须手动发生。我们希望应用程序自动切换到备份服务器，但我们不希望它们切换回主服务器，除非操作员已修复了任何问题，并决定再次中断应用程序是个好时机。

* 客户端应用程序的语义应该简单且易于开发人员理解。理想情况下，它们应该隐藏在客户端 API 中。

* 应该为网络架构师提供明确的说明，说明如何避免可能导致//裂脑综合征//的设计，其中双星对中的两个服务器都认为它们是活动服务器。

* 两个服务器的启动顺序不应有任何依赖关系。

* 必须能够在不停止客户端应用程序的情况下对任一服务器进行计划中的停止和重启（尽管它们可能会被迫重新连接）。

* 操作员必须能够随时监控两个服务器。

* 必须能够使用高速专用网络连接连接两个服务器。也就是说，故障转移同步必须能够使用特定的 IP 路由。

我们做出以下假设：

* 单个备份服务器提供足够的保险；我们不需要多层备份。

* 主服务器和备份服务器都同样能够承载应用程序负载。我们不会尝试在服务器之间平衡负载。

* 有足够的预算来支付一个几乎一直什么都不做的完全冗余备份服务器。

我们不尝试涵盖以下内容：

* 使用活动备份服务器或负载平衡。在双星对中，备份服务器处于非活动状态，在主服务器脱机之前不做任何有用的工作。

* 以任何方式处理持久消息或事务。我们假设存在不可靠（且可能不受信任）的服务器或双星对的网络。

* 网络的任何自动探索。双星对在网络中是手动且明确定义的，并且为应用程序所知（至少在它们的配置数据中）。

* 服务器之间状态或消息的复制。所有服务器端状态必须在故障转移时由应用程序重新创建。

以下是我们在双星中使用的关键术语：

* **主服务器**：通常或最初处于活动状态的服务器。

* **备份服务器**：通常处于被动状态的服务器。如果主服务器从网络中消失，它将变为活动状态，当客户端应用程序请求备份服务器连接时。

* **活动**：接受客户端连接的服务器。最多有一个活动服务器。

* **被动**：在主服务器消失时接管的服务器。请注意，当双星对正常运行时，主服务器处于活动状态，备份服务器处于被动状态。发生故障转移时，角色会切换。

要配置双星对，您需要：

1. 告诉主服务器备份服务器的位置。
2. 告诉备份服务器主服务器的位置。
3. 可选地，调整故障响应时间，这两个服务器必须相同。

主要的调优问题是你希望服务器检查其对等状态的频率，以及你希望多快激活故障转移。在我们的示例中，故障转移超时值默认为 2,000 毫秒。如果您减少此值，备份服务器将更快地接管为活动服务器，但可能会在主服务器可以恢复的情况下接管。例如，您可能已将主服务器包装在 shell 脚本中，如果主服务器崩溃，该脚本会重启它。在这种情况下，超时应该高于重启主服务器所需的时间。

为了使客户端应用程序与双星对正常工作，它们必须：

1. 知道两个服务器的地址。
2. 尝试连接到主服务器，如果失败，则连接到备份服务器。
3. 检测失败的连接，通常使用心跳。
4. 尝试重新连接到主服务器，然后备份（按此顺序），重试之间的延迟至少与服务器故障转移超时时间一样长。
5. 重新创建它们在服务器上所需的所有状态。
6. 如果在故障转移期间需要可靠的消息，则重新传输丢失的消息。

这不是简单的工作，我们通常将其包装在一个 API 中，向真正的最终用户应用程序隐藏它。

这些是双星模式的主要限制：

* 服务器进程不能是多个双星对的一部分。
* 主服务器可以有一个备份服务器，且只有一个。
* 被动服务器不做任何有用的工作，因此被浪费了。
* 备份服务器必须能够处理完整的应用程序负载。
* 故障转移配置无法在运行时修改。
* 客户端应用程序必须做一些工作才能从故障转移中受益。

### 防止裂脑综合征

//裂脑综合征//发生在集群的不同部分认为它们同时处于活动状态时。它会导致应用程序停止相互查看。双星有一个检测和消除裂脑的算法，该算法基于三方决策机制（服务器在获得应用程序连接请求且无法看到其对等服务器之前不会决定变为活动状态）。

然而，仍然有可能（错误地）设计一个网络来欺骗这个算法。一个典型的场景是一个双星对，分布在两座建筑物之间，每座建筑物还有一组应用程序，并且两座建筑物之间有一个网络链路。断开此链路将创建两组客户端应用程序，每组都有半个双星对，每个故障转移服务器都将变为活动状态。

为了防止裂脑情况，我们必须使用专用网络链路连接双星对，这可以简单到将它们都插入同一个交换机，或者更好的是，直接在两台机器之间使用交叉电缆。

我们不得将双星架构拆分为两个孤岛，每个孤岛都有一组应用程序。虽然这可能是常见的网络架构类型，但在这种情况下，您应该使用联合，而不是高可用性故障转移。

一个适当偏执的网络配置将使用两个专用集群互连，而不是一个。此外，用于集群的网络卡将与用于消息流量的网络卡不同，并且可能在服务器硬件上的不同路径上。目标是使网络中可能的故障与集群中可能的故障分开。网络端口可能具有相对较高的故障率。

## 无代理可靠性（自由职业者模式） {#Brokerless-Reliability-Freelance-Pattern}

专注于基于代理的可靠性似乎有些讽刺，当我们经常将 ZeroMQ 解释为"无代理消息传递"时。然而，在消息传递中，就像在现实生活中一样，中间人既是负担也是好处。在实践中，大多数消息传递架构都受益于分布式和代理消息传递的混合。当您能够自由决定想要做出的权衡时，您会得到最好的结果。这就是为什么我可以开车二十分钟去批发商那里为聚会买五箱葡萄酒，但我也可以步行十分钟去街角商店为晚餐买一瓶。我们对时间、精力和成本的上下文敏感相对估值对现实世界经济体至关重要。它们对最佳消息传递架构也至关重要。

这就是为什么 ZeroMQ 不//强加//以代理为中心的架构，尽管它确实为您提供了构建代理（又称//代理//）的工具，我们已经构建了十几个左右不同的代理，只是为了练习。

因此，我们将通过解构我们在本章前面构建的基于代理的可靠性，并将其转换回我称之为自由职业者模式的分布式点对点架构来结束本章。我们的用例将是一个名称解析服务。这是 ZeroMQ 架构中的一个常见问题：我们如何知道要连接的端点？在代码中硬编码 TCP/IP 地址是疯狂脆弱的。使用配置文件会创建管理噩梦。想象一下，如果您必须在您使用的每台 PC 或手机上手动配置 Web 浏览器，以意识到"google.com"是"74.125.230.82"。

ZeroMQ 名称服务（我们将制作一个简单的实现）必须执行以下操作：

* 将逻辑名称解析为至少一个绑定端点，以及一个连接端点。现实的名称服务将提供多个绑定端点，并且可能还提供多个连接端点。

* 允许我们管理多个并行环境，例如"测试"与"生产"，而无需修改代码。

* 可靠，因为如果它不可用，应用程序将无法连接到网络。

将名称服务放在面向服务的管家代理后面从某些角度来看是聪明的。然而，更简单且不那么令人惊讶的是，将名称服务公开为客户端可以直接连接的服务器。如果我们做得对，名称服务将成为我们在代码或配置文件中需要硬编码的//唯一//全局网络端点。

我们要处理的故障类型是服务器崩溃和重启、服务器忙循环、服务器过载和网络问题。为了获得可靠性，我们将创建一组名称服务器，因此如果一个崩溃或消失，客户端可以连接到另一个，等等。实际上，两个就足够了。但对于示例，我们将假设池可以是任何大小。

在这种架构中，大量客户端直接连接到少量服务器。服务器绑定到它们各自的地址。它从根本上不同于像管家这样的基于代理的方法，工人连接到代理。客户端有几个选项：

* 使用 REQ 套接字和懒惰海盗模式。简单，但需要一些额外的智能，这样客户端就不会愚蠢地尝试一遍又一遍地重新连接到死亡的服务器。

* 使用 DEALER 套接字并发送请求（这将负载平衡到所有连接的服务器），直到它们得到回复。有效，但不优雅。

* 使用 ROUTER 套接字，这样客户端就可以寻址特定的服务器。但是客户端如何知道服务器套接字的身份呢？要么服务器必须先 ping 客户端（复杂），要么服务器必须使用客户端已知的硬编码、固定身份（讨厌）。

我们将在以下小节中开发这些。

### 模型二：残酷的霰弹枪大屠杀

让我们将客户端切换到使用 DEALER 套接字。我们的目标在这里是确保我们在尽可能短的时间内得到回复，无论特定服务器是否启动或关闭。我们的客户端采用这种方法：

* 我们设置东西，连接到所有服务器。
* 当我们有请求时，我们会像拥有服务器数量一样多次发送它。
* 我们等待第一个回复，并接受它。
* 我们忽略任何其他回复。

实际发生的情况是，当所有服务器都在运行时，ZeroMQ 会分配请求，以便每个服务器获得一个请求并发送一个回复。当任何服务器脱机并断开连接时，ZeroMQ 会将请求分配给剩余的服务器。因此，服务器在某些情况下可能会多次获得相同的请求。

对客户端来说更令人讨厌的是，我们会得到多个回复，但没有保证我们会得到确切数量的回复。请求和回复可能会丢失（例如，如果服务器在处理请求时崩溃）。

因此，我们必须对请求进行编号，并忽略任何与请求编号不匹配的回复。我们的模型一服务器可以工作，因为它是一个回显服务器，但巧合并不是理解的好基础。因此，我们将制作一个模型二服务器，它会咀嚼消息并返回一个正确编号的回复，内容为"OK"。我们将使用由两部分组成的消息：序列号和正文。

以下是关于客户端实现需要注意的一些事项：

我们的霰弹枪方法的优点和缺点是：

* 优点：它简单、易于制作且易于理解。
* 优点：它完成了故障转移的工作，并且工作迅速，只要至少有一个服务器在运行。
* 缺点：它会产生冗余网络流量。
* 缺点：我们不能优先考虑我们的服务器，即主服务器，然后是辅助服务器。
* 缺点：服务器一次最多只能处理一个请求。

### 模型三：复杂和讨厌

霰弹枪方法看起来好得令人难以置信。让我们科学地研究所有替代方案。我们将探索复杂/讨厌的选项，即使这只是为了最终意识到我们更喜欢残酷。啊，我生活的故事。

我们可以通过切换到 ROUTER 套接字来解决客户端的主要问题。这让我们可以将请求发送到特定的服务器，避免我们知道已死亡的服务器，并且通常像我们想要的那样聪明。我们还可以通过切换到 ROUTER 套接字来解决服务器的主要问题（单线程）。

但在两个匿名套接字（尚未设置身份）之间进行 ROUTER 到 ROUTER 是不可能的。双方只有在收到第一条消息时才会为对方生成身份，因此任何一方都无法与对方对话，直到它先收到消息。摆脱这个难题的唯一方法是作弊，并在一个方向上使用硬编码身份。在客户端/服务器情况下作弊的正确方法是让客户端"知道"服务器的身份。反过来做将是疯狂的，除了复杂和讨厌之外，因为任何数量的客户端都应该能够独立出现。疯狂、复杂和讨厌是种族灭绝独裁者的伟大属性，但对软件来说是可怕的属性。

与其发明另一个需要管理的概念，我们将使用连接端点作为身份。这是双方都可以同意的唯一字符串，而无需比他们已经为霰弹枪模型拥有的更多先验知识。这是连接两个 ROUTER 套接字的偷偷摸摸且有效的方法。

记住 ZeroMQ 身份是如何工作的。服务器 ROUTER 套接字在绑定套接字之前设置身份。当客户端连接时，它们会做一个小的握手来交换身份，然后任何一方发送真实消息。客户端 ROUTER 套接字没有设置身份，向服务器发送空身份。服务器生成一个随机 UUID 来指定客户端供自己使用。服务器将其身份（我们同意将是一个端点字符串）发送给客户端。

这意味着我们的客户端可以在连接建立后立即向服务器路由消息（即，在其 ROUTER 套接字上发送，指定服务器端点作为身份）。这不是在 {{zmq_connect[3]}} 之后//立即//发生，而是在此之后的某个随机时间。这里有一个问题：我们不知道服务器何时会实际可用并完成其连接握手。如果服务器在线，可能是在几毫秒后。如果服务器关闭了，系统管理员出去吃午饭了，可能是一个小时后。

这里有一个小悖论。我们需要知道服务器何时连接并可用于工作。在自由职业者模式中，与我们之前在本章中看到的基于代理的模式不同，服务器在被询问之前是沉默的。因此，在我们询问它之前，我们无法与服务器对话，而它在我们询问它之前无法告诉我们它在线。

我的解决方案是混合一点来自模型 2 的霰弹枪方法，这意味着我们会向任何我们能触及的东西发射（无害的）射击，如果有任何动静，我们就知道它活着。我们不会发射真正的请求，而是一种 ping-pong 心跳。

## 结论 {#Conclusion}

在本章中，我们看到了各种可靠的请求 - 回复机制，每种机制都有一定的成本和收益。示例代码基本上可以用于实际使用，尽管它没有优化。在所有不同的模式中，有两个在生产使用中突出：管家模式，用于基于代理的可靠性，和自由职业者模式，用于无代理可靠性。
