## 请求 - 回复机制 {#The-Request-Reply-Mechanisms}

我们已经简单了解了多部分消息。现在让我们看一个主要用例，即*回复消息信封*。信封是一种安全地打包数据和地址的方式，而不触及数据本身。通过将回复地址分离到信封中，我们使得编写通用的中介如 API 和代理成为可能，它们可以创建、读取和删除地址，无论消息负载或结构是什么。

在请求 - 回复模式中，信封保存了回复的返回地址。这就是没有状态的 ZeroMQ 网络如何创建往返请求 - 回复对话的方式。

当你使用 REQ 和 REP 套接字时，你甚至看不到信封；这些套接字自动处理它们。但对于大多数有趣的请求 - 回复模式，你需要理解信封，特别是 ROUTER 套接字。我们将逐步介绍这个过程。

### 简单回复信封 {#The-Simple-Reply-Envelope}

请求 - 回复交换由一个*请求*消息，和一个最终的*回复*消息组成。在简单的请求 - 回复模式中，每个请求都有一个回复。在更高级的模式中，请求和回复可以异步流动。然而，回复信封的工作方式总是相同的。

ZeroMQ 回复信封正式由零个或多个回复地址组成，后跟一个空帧（信封分隔符），后跟消息体（零个或多个帧）。信封由链中的多个套接字共同创建。我们将分解这个过程。

我们首先通过 REQ 套接字发送"Hello"。REQ 套接字创建尽可能简单的回复信封，它没有地址，只有一个空分隔符帧和包含"Hello"字符串的消息帧。这是一个两帧消息。

{{< textdiagram name="fig26.png" figno="26" title="具有最小信封的请求" >}}
          #---#
Frame 1   | 0 |            空分隔符帧
          #---#-------#
Frame 2   | 5 | Hello |    数据帧
          #---+-------#
{{< /textdiagram >}}

REP 套接字做匹配的工作：它剥离信封，包括分隔符帧，保存整个信封，并将"Hello"字符串传递给应用程序。因此，我们原始的 Hello World 示例在内部使用了请求 - 回复信封，但应用程序从未看到它们。

如果你监视<tt>hwclient</tt>和<tt>hwserver</tt>之间流动的网络数据，你会看到：每个请求和每个回复实际上是两帧，一个空帧然后是主体。对于简单的 REQ-REP 对话来说，这似乎没有太大意义。然而，当我们探索 ROUTER 和 DEALER 如何处理信封时，你会看到原因。

### 扩展回复信封 {#The-Extended-Reply-Envelope}

现在让我们看看如果我们在 REP 和 REQ 套接字之间插入一个 ROUTER-DEALER 代理会发生什么。我们可以使用这个小型代理将多个客户端连接到多个服务器。这个代理必须打开两个套接字，一个前端（用于客户端）和一个后端（用于服务器）。在前端，它使用 ROUTER 套接字，该套接字将客户端地址添加到信封中。在后端，它使用 DEALER 套接字，该套接字将所有信封数据剥离。

{{< textdiagram name="fig27.png" figno="27" title="扩展请求 - 回复" >}}
     .---------.      .---------.      .---------.
     |  Client |      |  Proxy  |      |  Server |
     |   REQ   |      |  ROUTER |      |   REP   |
     '----+----'      +----+----+      '----+----'
          |              |  |              |
          '--------------+--+--------------'
                         |  |
                         v  v
{{< /textdiagram >}}

结果是扩展了请求 - 回复信封，它现在包含客户端的地址。这是 ROUTER 套接字所做的：它通过添加消息来自的节点的身份来扩展回复信封。

ROUTER 套接字创建扩展请求 - 回复信封。扩展信封格式是：

{{< textdiagram name="fig28.png" figno="28" title="扩展请求 - 回复信封" >}}
     #---------#  #---#  #-------#
     | Address |  | 0 |  |  Data |
     #---------#  #---#  #-------#
{{< /textdiagram >}}

当 REP 套接字剥离信封时，它得到客户端地址，并用它来路由回复。当我们有多个客户端时，每个客户端都会得到一个正确的回复。

### 探索 ROUTER 套接字 {#Exploring-ROUTER-Sockets}

让我们更仔细地看看 ROUTER 套接字。我们已经看到它通过添加消息来自的节点的身份来扩展回复信封。这个身份应该是如何使用的呢？

ROUTER 套接字为每个连接创建身份。如果身份是明确的，ROUTER 套接字会将身份作为信封中的第一帧传递给应用程序。如果身份不是明确的（这是常见情况），ROUTER 套接字会生成一个 5 字节的身份，该身份具有第 0 位设置为 1。

这意味着，当我们从 ROUTER 套接字接收消息时，我们需要：

1. 保存身份，以便我们可以将其用作回复时的地址。
2. 剥离空帧（信封分隔符）。
3. 将消息体传递给应用程序。

ROUTER 套接字是异步的。你可以从它们那里接收消息，也可以向它们发送消息。它们维护每个连接的状态，以便它们可以正确地将回复路由回原始请求者。

### 负载均衡模式 {#The-Load-Balancing-Pattern}

现在让我们看看负载均衡模式，这是请求 - 回复路由中最有用的模式之一。它允许我们将工作分配给多个工人，并在工人变得可用时将工作发送给他们。

负载均衡代理必须：

1. 接受来自客户端的请求。
2. 将这些请求分配给工人。
3. 将工人的回复返回给正确的客户端。

为了做到这一点，代理使用两个套接字：

* 一个 ROUTER 前端套接字，接受客户端请求。
* 一个 ROUTER 后端套接字，连接到工人。

代理维护一个可用工人的队列。当请求进来时，它从队列中取出一个工人，并将请求发送给该工人。当工人回复时，代理将回复返回给原始客户端，并将工人重新添加到可用队列中。

这种模式非常强大，因为它允许我们：

* 动态添加和删除工人。
* 优雅地处理工人的故障。
* 在工人之间分配工作负载。

### 工作示例：代理间路由 {#Worked-Example-Inter-Broker-Routing}

现在让我们把我们迄今为止看到的一切都用上，并将事情扩展到真正的应用程序。我们将分几个迭代逐步构建这个。我们最好的客户紧急打电话，要求设计一个大型云计算设施。他对跨越多个数据中心的云有一个愿景，每个数据中心都是客户端和工人的集群，并且作为一个整体协同工作。

因为我们足够聪明，知道实践总是胜过理论，我们建议制作一个使用 ZeroMQ 的工作模拟。我们的客户，渴望在他的老板改变主意之前锁定预算，并且在 Twitter 上看到了关于 ZeroMQ 的好消息，同意了。

#### 建立细节 {#Establishing-the-Details}

几杯浓缩咖啡之后，我们想要跳入编写代码，但一个微小的声音告诉我们在为完全错误的问题制作 sensational 解决方案之前获取更多细节。"云正在做什么样的工作？"，我们问。

客户解释：

* 工人在各种硬件上运行，但它们都能够处理任何任务。每个集群有几百个工人，总共有十几个集群。

* 客户端为工人创建任务。每个任务都是一个独立的工作单元，客户端只想找到一个可用的工人，并尽快将任务发送给它。会有很多客户端，它们会任意来去。

* 真正的困难是能够在任何时候添加和删除集群。集群可以立即离开或加入云，带来其所有工人和客户端。

* 如果它们自己的集群中没有工人，客户端的任务将转到云中其他可用的工人。

* 客户端一次发送一个任务，等待回复。如果它们在 X 秒内没有得到答案，它们会再次发送任务。这不关我们的事；客户端 API 已经这样做了。

* 工人一次处理一个任务；它们是非常简单的生物。如果它们崩溃，它们会被启动它们的任何脚本重新启动。

所以我们仔细检查，确保我们正确理解了这一点：

* "集群之间会有某种超级网络互连，对吧？"，我们问。客户说，"是的，当然，我们不是白痴。"

* "我们谈论的是什么样的数量？"，我们问。客户回答说，"每个集群多达一千个客户端，每个客户端每秒最多十个请求。请求很小，回复也很小，每个不超过 1K 字节。"

所以我们做了一些小计算，发现这将通过普通 TCP 很好地工作。2,500 个客户端 x 10/秒x 1,000 字节 x 2 个方向= 50MB/秒或400Mb/秒，对于1Gb网络来说不是问题。

这是一个需要 no exotic 硬件或协议的直接问题，只是一些 clever 路由算法和仔细的设计。我们首先设计一个集群（一个数据中心），然后我们弄清楚如何将集群连接在一起。

#### 单个集群的架构 {#Architecture-of-a-Single-Cluster}

工人和客户端是同步的。我们想要使用负载均衡模式将任务路由给工人。工人都是相同的；我们的设施没有不同服务的概念。工人是匿名的；客户端从不直接寻址它们。我们在这里不做任何努力来提供 guaranteed 交付、重试等。

出于我们已经检查过的原因，客户端和工人不会直接相互对话。动态添加或删除节点变得 impossible。因此，我们的基本模型包含我们之前看到的请求 - 回复消息代理。

问题是：我们如何使每个集群的客户端与另一个集群的工人对话？有几种可能性，每种都有优点和缺点：

* 客户端可以直接连接到两个代理。优点是我们不需要修改代理或工人。但客户端会变得更复杂，并且需要了解整体拓扑结构。如果我们想添加第三个或第四个集群，所有客户端都会受到影响。实际上，我们必须将路由和故障转移逻辑移到客户端中，这并不好。

* 工人可能直接连接到两个代理。但 REQ 工人无法做到这一点，它们只能回复一个代理。我们可能会使用 REP，但 REP 不提供可定制的代理到工人路由（如负载均衡），只有内置的负载均衡。这是失败的；如果我们想将工作分配给空闲的工人，我们恰恰需要负载均衡。一个解决方案是为工人节点使用 ROUTER 套接字。我们将其标记为"想法#1"。

* 代理可以相互连接。这看起来最整洁，因为它创建了最少的额外连接。我们无法动态添加集群，但这可能在范围之外。现在客户端和工人对真实网络拓扑保持无知，代理在有空闲容量时相互通知。我们将其标记为"想法#2"。

让我们探索想法#1。在这种模型中，我们有工人连接到两个代理并从任一代理接受工作。

这看起来可行。然而，它并没有提供我们想要的，即客户端尽可能获得本地工人，只有在比等待更好的情况下才获得远程工人。此外，工人将向两个代理发出"就绪"信号，并且可以同时获得两个工作，而其他工人仍然空闲。似乎这个设计失败了，因为我们再次将路由逻辑放在了边缘。

所以，想法#2。我们互连代理，不接触客户端或工人，它们是我们习惯的 REQ。

这个设计很有吸引力，因为问题在一个地方解决，对世界其他地方不可见。基本上，代理彼此打开秘密通道，像骆驼商人一样耳语，"嘿，我有一些空闲容量。如果你有太多客户端，给我个喊声，我们会处理"。

实际上，它只是一个更复杂的路由算法：代理成为彼此的承包商。在我们使用真实代码之前，这个设计还有其他值得喜欢的地方：

* 它将常见情况（同一集群上的客户端和工人）视为默认情况，为例外情况（在集群之间转移工作）做额外工作。

* 它让我们可以为不同类型的工作使用不同的消息流。这意味着我们可以不同地处理它们，例如，使用不同类型的网络连接。

* 感觉像是能够平滑扩展。互连三个或更多代理不会变得过于复杂。如果我们发现这是个问题，很容易通过添加超级代理来解决。

我们现在将制作一个工作示例。我们将整个集群打包到一个进程中。这显然不现实，但它使模拟变得简单，并且模拟可以准确地扩展到真实进程。这就是 ZeroMQ 的美妙之处——你可以在微观层面设计，并将其扩展到宏观层面。线程变成进程，然后变成盒子，模式和逻辑保持不变。我们的每个"集群"进程包含客户端线程、工人线程和代理线程。

我们知道基本模型：

* REQ 客户端（REQ）线程创建工作负载并将其传递给代理（ROUTER）。
* REQ 工人（REQ）线程处理工作负载并将结果返回给代理（ROUTER）。
* 代理使用负载均衡模式排队和分配工作负载。

### 联合与对等 {#Federation-Versus-Peering}

有几种可能的代理互连方式。我们想要的是能够告诉其他代理"我们有容量"，然后接收多个任务。我们还需要能够告诉其他代理"停止，我们满了"。它不需要完美；有时我们可能会接受无法立即处理的工作，然后我们会尽快完成。

最简单的互连是*联合*，其中代理为彼此模拟客户端和工人。我们通过将我们的前端连接到其他代理的后端套接字来实现这一点。请注意，将套接字绑定到端点并将其连接到其他端点是合法的。

这将为我们提供两个代理中的简单逻辑和一个相当好的机制：当没有工人时，告诉其他代理"准备好了"，并从它那里接受一个工作。问题是它对于这个问题来说太简单了。联合代理一次只能处理一个任务。如果代理模拟锁步客户端和工人，那么根据定义它也将是锁步的，如果它有很多可用的工人，它们将不会被使用。我们的代理需要以完全异步的方式连接。

联合模型对于其他类型的路由来说是完美的，特别是面向服务的架构（SOA），它们通过服务名称和邻近性而不是负载均衡或轮询来路由。所以不要认为它没用，它只是不适合所有用例。

让我们看看*对等*方法，其中代理明确地意识到彼此并通过特权通道进行通信。让我们分解一下，假设我们想要互连 N 个代理。每个代理有（N-1）个对等点，所有代理都使用完全相同的代码和逻辑。代理之间有两种不同的信息流：

* 每个代理需要告诉其对等点它在任何时候有多少可用的工人。这可以是相当简单的信息——只是一个定期更新的数量。显而易见（且正确）的套接字模式是发布 - 订阅。因此，每个代理打开一个 PUB 套接字并在其上发布状态信息，每个代理还打开一个 SUB 套接字并将其连接到每个其他代理的 PUB 套接字，以从其对等点获取状态信息。

* 每个代理需要一种方式将任务委托给对等点并异步地获得回复。我们将使用 ROUTER 套接字来完成这个；没有其他组合可以工作。每个代理有两个这样的套接字：一个用于它接收的任务，一个用于它委托的任务。如果我们不使用两个套接字，那么每次知道我们是读取请求还是回复就会更加困难。这将意味着向消息信封添加更多信息。

代理与其本地客户端和工人之间也有信息流。

### 命名仪式 {#The-Naming-Ceremony}

三个流 × 每个流两个套接字 = 我们在代理中必须管理的六个套接字。选择好的名称对于在我们脑海中保持多路套接字杂耍表演相当连贯至关重要。套接字*做*某事，它们所做的事情应该构成它们名称的基础。这是为了在几周后的一个寒冷的周一早晨喝咖啡之前阅读代码时不会感到任何痛苦。

让我们为套接字做一个萨满命名仪式。三个流是：

* 代理与其客户端和工人之间的*本地*请求 - 回复流。
* 代理与其对等代理之间的*云*请求 - 回复流。
* 代理与其对等代理之间的*状态*流。

找到长度相同的有意义的名称意味着我们的代码将很好地对齐。这不是什么大事，但关注细节有帮助。对于每个流，代理有两个套接字，我们可以正交地称为*前端*和*后端*。我们经常使用这些名称。前端接收信息或任务。后端将这些发送给其他对等点。概念流是从前到后（回复从后到前相反方向）。

因此，在我们为本教程编写的所有代码中，我们将使用这些套接字名称：

* *localfe* 和 *localbe* 用于本地流。
* *cloudfe* 和 *cloudbe* 用于云流。
* *statefe* 和 *statebe* 用于状态流。

对于我们的传输，并且因为我们在一个盒子上模拟整个事情，我们将使用<tt>ipc</tt>来处理所有事情。这具有像<tt>tcp</tt>一样在连接性方面工作的优点（即，它是一个断开连接的传输，不像<tt>inproc</tt>），但我们不需要 IP 地址或 DNS 名称，这在这里会很痛苦。相反，我们将使用称为*某事*-<tt>local</tt>、*某事*-<tt>cloud</tt>和*某事*-<tt>state</tt>的<tt>ipc</tt>端点，其中*某事*是我们模拟集群的名称。

你可能会认为这对于一些名称来说是很多工作。为什么不称它们为 s1、s2、s3、s4 等？答案是，如果你的大脑不是完美的机器，你在阅读代码时需要很多帮助，我们将看到这些名称确实有帮助。记住"三个流，两个方向"比"六个不同的套接字"更容易。

### 原型本地和云流 {#Prototyping-the-Local-and-Cloud-Flows}

现在我们有了状态流，我们可以添加本地和云流。这些是请求 - 回复流，因此我们需要以不同的方式处理它们。

本地流在代理和其本地客户端和工人之间。云流在代理和其对等代理之间。

本地流的工作方式如下：

1. 客户端发送请求到代理。
2. 代理接收请求并将其路由到本地工人或云。
3. 工人处理请求并将回复发送回代理。
4. 代理将回复发送回客户端。

云流的工作方式如下：

1. 代理从其对等代理接收请求。
2. 代理将请求路由到其本地工人。
3. 工人处理请求并将回复发送回代理。
4. 代理将回复发送回对等代理。

* 客户端线程检测并报告失败的请求。它们通过轮询响应来做到这一点，如果 10 秒后没有响应，则打印错误消息。

这些是开发此程序期间出现的一些问题：

* 客户端会冻结，由于请求或回复在某个地方丢失。回想一下，ROUTER 套接字会丢弃它无法路由的消息。这里的第一个策略是修改客户端线程以检测和报告此类问题。其次，我在主循环中的每次接收后放置了<tt>zmsg_dump()</tt>调用，直到问题的根源变得清晰。

* 主循环错误地从多个就绪套接字读取。这导致第一条消息丢失。我通过只从第一个就绪套接字读取来修复这个问题。

* <tt>zmsg</tt>类没有正确地将 UUID 编码为 C 字符串。这导致包含 0 字节的 UUID 损坏。我通过修改<tt>zmsg</tt>来将 UUID 编码为可打印的十六进制字符串来修复这个问题。

## 总结 {#Chapter-Summary}

在本章中，我们探讨了 ZeroMQ 的高级请求 - 回复模式。我们已经看到了如何：

* 使用请求 - 回复信封来路由消息。
* 使用 ROUTER 和 DEALER 套接字来创建复杂的模式。
* 构建负载均衡代理来分配工作。
* 设计高级 API 来简化 ZeroMQ 的使用。
* 构建异步请求 - 回复服务器。
* 创建可以跨越多个集群的代理间路由系统。

这些模式非常强大，它们允许我们构建可以处理复杂工作负载的分布式系统。它们还展示了 ZeroMQ 的灵活性和表现力。

在下一章中，我们将探讨 ZeroMQ 的可靠请求 - 回复模式，它们允许我们构建可以处理故障的分布式系统。
