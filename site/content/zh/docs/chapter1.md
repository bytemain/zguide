# 第 1 章 - 基础 {#basics}

## 修复世界 {#Fixing-the-World}

如何解释 ZeroMQ？有些人从它所做的所有美妙事情开始说起。*它是类固醇上的套接字。它就像带路由的邮箱。它很快！* 其他人试图分享他们的启蒙时刻，那种顿悟范式转变的时刻，当一切都变得明显时。*事情变得更简单了。复杂性消失了。它打开了思维。* 其他人试图通过比较来解释。*它更小、更简单，但仍然看起来很熟悉。* 就我个人而言，我喜欢记住我们为什么制作 ZeroMQ，因为这很可能是你，读者，今天仍然所处的位置。

编程是伪装成艺术的科学，因为我们大多数人都不理解软件的物理学，而且很少被教授。软件的物理学不是算法、数据结构、语言和抽象。这些只是我们制造、使用、丢弃的工具。软件的真正物理学是人类的物理学——具体来说，是我们在复杂性方面的局限性，以及我们共同努力分块解决大型问题的愿望。这就是编程的科学：制造人们可以*轻松*理解和使用的构建块，人们将共同努力解决最大的问题。

我们生活在一个互联的世界中，现代软件必须在这个世界中导航。因此，明天最大解决方案的构建块是互联且大规模并行的。代码不再只是"强大而沉默"。代码必须与代码对话。代码必须健谈、社交、连接良好。代码必须像人脑一样运行，数万亿个单独的神经元相互发送消息，一个大规模并行网络，没有中央控制，没有单点故障，但仍能够解决极其困难的问题。代码的未来看起来像人脑并非偶然，因为每个网络的端点，在某种程度上，都是人脑。

如果你做过任何线程、协议或网络方面的工作，你会意识到这几乎是不可能的。这是一个梦想。即使通过几个套接字连接几个程序，在处理现实生活情况时也会变得相当糟糕。数万亿？成本将是无法想象的。连接计算机如此困难，以至于为此提供软件和服务是一个价值数十亿美元的业务。

所以我们生活在一个布线能力超前于我们使用能力的世界中。我们在 20 世纪 80 年代遇到了软件危机，当时领先的软件工程师 Fred Brooks 认为 [没有"银弹"](http://en.wikipedia.org/wiki/No_Silver_Bullet) 可以"承诺生产力、可靠性或简单性提高一个数量级"。

Brooks 错过了免费和开源软件，这解决了那场危机，使我们能够高效地共享知识。今天我们面临另一个软件危机，但我们不太谈论它。只有最大、最富有的公司才能负担得起创建连接的应用程序。有一个云，但它是专有的。我们的数据和知识正在从我们的个人电脑中消失，进入我们无法访问、无法竞争的云中。谁拥有我们的社交网络？这就像大型机-PC 革命的逆转。

我们可以把政治哲学 [留给另一本书](http://cultureandempire.com)。关键是，虽然互联网提供了大规模连接代码的潜力，但现实是，这对我们大多数人来说是遥不可及的，因此大型有趣的问题（在健康、教育、经济、交通等方面）仍未解决，因为没有连接代码的方法，因此也没有连接可以共同努力解决这些问题的大脑的方法。

已经有许多尝试来解决连接代码的挑战。有数千个 IETF 规范，每个都解决了谜题的一部分。对于应用程序开发人员来说，HTTP 可能是一个足够简单的解决方案，但它可以说通过鼓励开发人员和架构师思考大型服务器和瘦、愚蠢的客户端而使问题变得更糟。

所以今天人们仍然使用原始 UDP 和 TCP、专有协议、HTTP 和 Websockets 来连接应用程序。它仍然痛苦、缓慢、难以扩展，并且本质上是集中的。分布式 P2P 架构主要用于娱乐，而不是工作。有多少应用程序使用 Skype 或 Bittorrent 来交换数据？

这把我们带回了编程的科学。为了修复世界，我们需要做两件事。第一，解决"如何随时随地将任何代码连接到任何代码"的一般问题。第二，将其包装在最简单的构建块中，人们可以*轻松*理解和使用。

听起来简单得可笑。也许确实如此。这就是重点所在。

## 关于字符串的小注释 {#A-Minor-Note-on-Strings}

ZeroMQ 除了字节大小外，对你发送的数据一无所知。这意味着你有责任安全地格式化它，以便应用程序可以读回它。为对象和复杂数据类型做这个工作是 Protocol Buffers 等专业库的工作。但即使对于字符串，你也需要小心。

在 C 和其他一些语言中，字符串以空字节结尾。我们可以发送一个像"HELLO"这样的字符串，并带上那个额外的空字节：

```C
zmq_send (requester, "Hello", 6, 0);
```

然而，如果你从另一种语言发送字符串，它可能不会包含那个空字节。例如，当我们在 Python 中发送相同的字符串时，我们这样做：

```Python
socket.send ("Hello")
```

然后传到网络上的东西是一个长度（较短的字符串为一个字节）和作为单个字符的字符串内容。

{{< textdiagram name="fig3.png" figno="3" title="A ZeroMQ string" >}}
#-----#  #-----+-----+-----+-----+-----#
|  5  |  |  H  |  e  |  l  |  l  |  o  |
#-----#  #-----+-----+-----+-----+-----#
{{< /textdiagram >}}

如果你从 C 程序中读取这个，你会得到看起来像一个字符串的东西，并且可能意外地像一个字符串一样工作（如果幸运的话，这五个字节后面跟着一个无辜潜伏的空值），但它不是一个合适的字符串。当你的客户端和服务器在字符串格式上不一致时，你会得到奇怪的结果。

当你从 ZeroMQ 接收字符串数据时，在 C 中，你根本不能相信它是安全终止的。每次读取字符串时，你都应该分配一个带有额外字节空间的新缓冲区，复制字符串，并用空值正确终止它。

因此，让我们建立规则，**ZeroMQ 字符串是指定长度的，并且在网络上发送时*没有*尾随空值**。在最简单的情况下（我们将在示例中这样做），ZeroMQ 字符串整齐地映射到 ZeroMQ 消息帧，它看起来像上面的图——一个长度和一些字节。

这是我们需要在 C 中做的，以接收 ZeroMQ 字符串并将其作为有效的 C 字符串传递给应用程序：

```C
//  从套接字接收 ZeroMQ 字符串并转换为 C 字符串
//  如果字符串超过 255 个字符，则在 255 处截断
static char *
s_recv (void *socket) {
    char buffer [256];
    int size = zmq_recv (socket, buffer, 255, 0);
    if (size == -1)
        return NULL;
    if (size > 255)
        size = 255;
    buffer [size] = '\0';
    /* 在*nix 中使用 strndup(buffer, sizeof(buffer)-1) */
    return strdup (buffer);
}
```

这成了一个方便的帮助函数，本着制作我们可以有益地重用的东西的精神，让我们写一个类似的<tt>s_send</tt>函数，以正确的 ZeroMQ 格式发送字符串，并将其打包成一个我们可以重用的头文件。

结果是<tt>zhelpers.h</tt>，它让我们用 C 编写更甜美、更短的 ZeroMQ 应用程序。这是一个相当长的源代码，只对 C 开发人员有趣，所以 [在闲暇时阅读它](https://github.com/imatix/zguide/blob/master/examples/C/zhelpers.h)。

注意，当你使用 SUB 套接字时，**必须**使用<tt>[zmq_setsockopt()](http://api.zeromq.org/master:zmq_setsockopt)</tt>和 SUBSCRIBE 设置订阅，如本代码所示。如果你不设置任何订阅，你将不会收到任何消息。这是初学者的常见错误。订阅者可以设置许多订阅，这些订阅会累加在一起。也就是说，如果更新匹配*任何*订阅，订阅者就会收到它。订阅者也可以取消特定的订阅。订阅通常是但不一定总是可打印的字符串。请参阅<tt>[zmq_setsockopt()](http://api.zeromq.org/master:zmq_setsockopt)</tt>了解其工作原理。

PUB-SUB 套接字对是异步的。客户端执行<tt>[zmq_recv()](http://api.zeromq.org/master:zmq_recv)</tt>，在一个循环中（或一次，如果这就是它所需要的）。试图向 SUB 套接字发送消息将导致错误。同样，服务根据需要经常执行<tt>[zmq_send()](http://api.zeromq.org/master:zmq_send)</tt>，但不得在 PUB 套接字上执行<tt>[zmq_recv()](http://api.zeromq.org/master:zmq_recv)</tt>。

理论上，使用 ZeroMQ 套接字，哪个端连接哪个端绑定并不重要。然而，在实践中存在未记录的区别，我稍后会讲到。现在，绑定 PUB 并连接 SUB，除非你的网络设计使这不可能。

关于 PUB-SUB 套接字还有一件更重要的事情需要知道：你不知道订阅者何时开始精确地获取消息。即使你启动一个订阅者，等待一段时间，然后启动发布者，**订阅者总是会错过发布者发送的第一条消息**。这是因为当订阅者连接到发布者（这需要一小段时间）时，发布者可能已经在发送消息了。

这种"慢加入者"症状经常困扰足够多的人，以至于我们将详细解释它。记住，ZeroMQ 执行异步 I/O，即在后台执行。假设你有两个节点按此顺序执行此操作：

* 订阅者连接到端点并接收和计数消息。
* 发布者绑定到端点并立即发送 1,000 条消息。

然后订阅者很可能不会收到任何消息。你会眨眼，检查你是否设置了正确的过滤器，然后重试，订阅者仍然不会收到任何消息。

建立 TCP 连接涉及往返握手，根据你的网络和节点之间的跳数，需要几毫秒。在那段时间里，ZeroMQ 可以发送许多消息。为了论证起见，假设建立连接需要 5 毫秒，同一链路每秒可以处理 1M 条消息。在订阅者连接到发布者的 5 毫秒期间，发布者只需要 1 毫秒就可以发送出这 1K 条消息。

在 [第 2 章 - 套接字和模式](chapter2#sockets-and-patterns) 中，我们将解释如何同步发布者和订阅者，以便在你真正连接并准备好之前不会开始发布数据。有一种简单愚蠢的方法可以延迟发布者，那就是 sleep。不要在真正的应用程序中这样做，因为它极其脆弱、不优雅且缓慢。使用 sleep 来证明发生了什么，然后等待 [第 2 章 - 套接字和模式](chapter2#sockets-and-patterns) 来看看如何正确地做到这一点。

同步的替代方案是简单地假设发布的数据流是无限的，没有开始也没有结束。人们还假设订阅者不关心它启动之前发生了什么。这就是我们构建天气客户端示例的方式。

因此，客户端订阅其选择的邮政编码，并收集该邮政编码的 100 个更新。这意味着来自服务器的约一千万个更新，如果邮政编码是随机分布的。你可以启动客户端，然后启动服务器，客户端将继续工作。你可以根据需要经常停止和重新启动服务器，客户端将继续工作。当客户端收集到一百个更新后，它会计算平均值，打印出来，然后退出。

关于发布 - 订阅（pub-sub）模式的一些要点：

* 订阅者可以连接到多个发布者，每次使用一个连接调用。数据将到达并被交错（"公平排队"），因此没有一个发布者会淹没其他发布者。

* 如果发布者没有连接的订阅者，那么它将简单地丢弃所有消息。

* 如果你使用 TCP 并且订阅者很慢，消息将在发布者上排队。我们稍后将看看如何使用"高水位标记"来保护发布者免受这种情况的影响。

* 从 ZeroMQ v3.x 开始，使用连接的协议（<tt>tcp:@<*>@</tt>或<tt>ipc:@<*>@</tt>）时，过滤发生在发布者端。使用<tt>epgm:@<//>@</tt>协议时，过滤发生在订阅者端。在 ZeroMQ v2.x 中，所有过滤都发生在订阅者端。

以下是在我的笔记本电脑上接收和过滤 10M 条消息需要多长时间，这是一台 2011 年的 Intel i5，不错但没什么特别的：

```
$ time wuclient

real    0m4.470s
user    0m0.000s
sys     0m0.008s
```

## ZeroMQ 编程 {#Programming-with-ZeroMQ}

看过一些例子后，你一定渴望开始在一些应用程序中使用 ZeroMQ。在你开始之前，深呼吸，放松一下，反思一些基本的建议，这些建议将为你节省很多压力和困惑。

* 逐步学习 ZeroMQ。它只是一个简单的 API，但它隐藏了无限可能的世界。慢慢掌握每一个可能性。

* 编写漂亮的代码。丑陋的代码隐藏问题，使别人难以帮助你。你可能习惯了无意义的变量名，但阅读你代码的人不会。使用真实的词作为名称，这些词能说明一些问题，而不是"我太粗心了，没告诉你这个变量真正是做什么的"。使用一致的缩进和干净的布局。编写漂亮的代码，你的世界会更舒适。

* 在编写时测试你制作的东西。当你的程序不工作时，你应该知道是哪五行代码出了问题。当你做 ZeroMQ 魔法时，这一点尤其重要，它第一次尝试时*不会*工作。

* 当你发现事情没有按预期工作时，把你的代码分解成块，测试每一块，看看哪一块不工作。ZeroMQ 让你制作本质上模块化的代码；利用这一点为你带来优势。

* 根据需要制作抽象（类、方法等）。如果你复制/粘贴大量代码，你也会复制/粘贴错误。

### 正确使用上下文 {#Getting-the-Context-Right}

ZeroMQ 应用程序总是通过创建*上下文*开始，然后使用它来创建套接字。在 C 中，这是<tt>[zmq_ctx_new()](http://api.zeromq.org/master:zmq_ctx_new)</tt>调用。你应该在进程中创建并使用恰好一个上下文。从技术上讲，上下文是单个进程中所有套接字的容器，并充当<tt>inproc</tt>套接字的传输，<tt>inproc</tt>套接字是连接一个进程中线程的最快方式。如果在运行时一个进程有两个上下文，这些就像单独的 ZeroMQ 实例。如果这是你明确想要的，好的，但否则记住：

**在进程开始时调用<tt>[zmq_ctx_new()](http://api.zeromq.org/master:zmq_ctx_new)</tt>一次，在结束时调用<tt>[zmq_ctx_destroy()](http://api.zeromq.org/master:zmq_ctx_destroy)</tt>一次。**

如果你使用<tt>fork()</tt>系统调用，在 fork 之后和子进程代码的开头执行<tt>[zmq_ctx_new()](http://api.zeromq.org/master:zmq_ctx_new)</tt>。一般来说，你想在子进程中做有趣的（ZeroMQ）事情，在父进程中做无聊的进程管理。

### 干净地退出 {#Making-a-Clean-Exit}

优雅的程序员与优雅的杀手有着相同的座右铭：完成工作时总是清理。当你使用 Python 这样的语言中的 ZeroMQ 时，东西会自动为你释放。但当使用 C 时，你必须仔细释放对象，当你完成它们时，否则你会得到内存泄漏、不稳定的应用程序，以及通常不好的业力。

内存泄漏是一回事，但 ZeroMQ 对你如何退出应用程序非常挑剔。原因技术性强且痛苦，但结果是，如果你留下任何套接字打开，<tt>[zmq_ctx_destroy()](http://api.zeromq.org/master:zmq_ctx_destroy)</tt>函数将永远挂起。即使你关闭所有套接字，<tt>[zmq_ctx_destroy()](http://api.zeromq.org/master:zmq_ctx_destroy)</tt>默认情况下会永远等待，如果有挂起的连接或发送，除非你在关闭它们之前在这些套接字上将 LINGER 设置为零。

我们需要担心的 ZeroMQ 对象是消息、套接字和上下文。幸运的是，在简单程序中这相当简单：

* 尽可能使用<tt>[zmq_send()](http://api.zeromq.org/master:zmq_send)</tt>和<tt>[zmq_recv()](http://api.zeromq.org/master:zmq_recv)</tt>，因为它避免了使用 zmq_msg_t 对象的需要。

* 如果你使用<tt>[zmq_msg_recv()](http://api.zeromq.org/master:zmq_msg_recv)</tt>，总是在完成后立即释放接收到的消息，通过调用<tt>[zmq_msg_close()](http://api.zeromq.org/master:zmq_msg_close)</tt>。

* 如果你打开和关闭大量套接字，这可能是一个迹象，表明你需要重新设计你的应用程序。在某些情况下，套接字句柄在你销毁上下文之前不会被释放。

* 当你退出程序时，关闭你的套接字，然后调用<tt>[zmq_ctx_destroy()](http://api.zeromq.org/master:zmq_ctx_destroy)</tt>。这会销毁上下文。

这至少是 C 开发的情况。在具有自动对象销毁的语言中，套接字和上下文将在你离开作用域时被销毁。如果你使用异常，你将不得不在类似"final"块的东西中进行清理，与任何资源一样。

如果你在做多线程工作，这比这复杂得多。我们将在下一章中讨论多线程，但因为你们中的一些人会不顾警告，试图在安全行走之前跑步，以下是*多线程*ZeroMQ 应用程序中干净退出的快速而肮脏的指南。

首先，不要试图从多个线程使用相同的套接字。请不要解释为什么你认为这将是极好的乐趣，只是请不要这样做。接下来，你需要关闭每个有正在进行请求的套接字。正确的方法是设置一个低的 LINGER 值（1 秒），然后关闭套接字。如果你的语言绑定在你销毁上下文时没有自动为你做这件事，我建议发送一个补丁。

最后，销毁上下文。这将导致任何阻塞的接收或轮询或发送在附加线程（即共享相同上下文的线程）中返回错误。捕获该错误，然后在*该*线程中设置 linger 并关闭套接字，然后退出。不要两次销毁相同的上下文。<tt>zmq_ctx_destroy</tt>在主线程中将阻塞，直到它知道的所有套接字都安全关闭。

瞧！它足够复杂和痛苦，以至于任何值得他或她盐分的语言绑定作者都会自动做这件事，使套接字关闭舞蹈变得不必要。

## 我们为什么需要 ZeroMQ {#Why-We-Needed-ZeroMQ}

现在你已经看到了 ZeroMQ 的实际应用，让我们回到"为什么"。

如今许多应用程序由跨越某种网络的组件组成，无论是局域网还是互联网。因此，许多应用程序开发人员最终都会进行某种消息传递。一些开发人员使用消息队列产品，但大多数时候他们自己使用 TCP 或 UDP 来做。这些协议并不难使用，但在从 A 到 B 发送几个字节与以任何可靠方式进行消息传递之间存在很大差异。

让我们看看当我们开始使用原始 TCP 连接部件时面临的典型问题。任何可重用的消息传递层都需要解决所有这些或大部分问题：

* 我们如何处理 I/O？我们的应用程序是阻塞的，还是我们在后台处理 I/O？这是一个关键的设计决策。阻塞 I/O 创建的架构不能很好地扩展。但后台 I/O 可能很难正确处理。

* 我们如何处理动态组件，即暂时离开的部件？我们是否正式将组件拆分为"客户端"和"服务器"并要求服务器不能消失？如果我们想要连接服务器到服务器呢？我们是否尝试每隔几秒钟重新连接一次？

* 我们如何表示网络上的消息？我们如何框架数据，使其易于编写和读取，免受缓冲区溢出，对小消息高效，但足以容纳戴着派对帽子的跳舞猫的最大视频？

* 我们如何处理我们无法立即传递的消息？特别是，如果我们正在等待一个组件重新上线？我们是否丢弃消息，将它们放入数据库，或放入内存队列？

* 我们在哪里存储消息队列？如果从队列读取的组件非常慢，导致我们的队列堆积，会发生什么？我们的策略是什么？

* 我们如何处理丢失的消息？我们是否等待新数据，请求重发，或者我们是否构建某种可靠性层，确保消息不会丢失？如果那一层本身崩溃了呢？

* 如果我们需要使用不同的网络传输。比如说，多播而不是 TCP 单播？或者 IPv6？我们是否需要重写应用程序，或者传输是否在某层中被抽象？

* 我们如何路由消息？我们是否可以将相同的消息发送给多个对等体？我们是否可以将回复发送回原始请求者？

* 我们如何为另一种语言编写 API？我们是否重新实现线级协议，或者我们是否重新打包库？如果是前者，我们如何保证高效和稳定的堆栈？如果是后者，我们如何保证互操作性？

* 我们如何表示数据，以便它可以在不同架构之间读取？我们是否强制执行特定编码的数据类型？这在多大程度上是消息传递系统的工作，而不是更高层的工作？

* 我们如何处理网络错误？我们是否等待并重试，默默地忽略它们，还是中止？

以一个典型的开源项目为例，比如 [Hadoop Zookeeper](https://zookeeper.apache.org/)，并阅读 C API 代码<tt>[src/c/src/zookeeper.c](http://github.com/apache/zookeeper/blob/trunk/src/c/src/zookeeper.c)</tt>。当我读到这段代码时，在 2013 年 1 月，它是 4,200 行的谜团，其中有一个未记录的客户端/服务器网络通信协议。我看到它很高效，因为它使用<tt>poll</tt>而不是<tt>select</tt>。但实际上，Zookeeper 应该使用通用的消息传递层和明确记录的线级协议。团队一遍又一遍地构建这个特定的轮子是非常浪费的。

但是如何制作可重用的消息传递层呢？为什么，当这么多项目需要这项技术时，人们仍然通过在他们的代码中驱动 TCP 套接字，一遍又一遍地解决那个长列表中的问题，来做困难的方式？

事实证明，构建可重用的消息传递系统真的非常困难，这就是为什么很少有 FOSS 项目尝试过，以及为什么商业消息传递产品复杂、昂贵、不灵活且脆弱。2006 年，iMatix 设计了 [AMQP](http://www.amqp.org)，它开始为 FOSS 开发人员提供可能是第一个可重用消息传递系统的配方。AMQP 比其他许多设计工作得更好，[但仍然相对复杂、昂贵且脆弱](https://web.archive.org/web/20190620095529/www.imatix.com/articles:whats-wrong-with-amqp)。需要几周时间来学习使用，并且需要几个月时间来创建在事情变得棘手时不会崩溃的稳定架构。

大多数消息传递项目，如 AMQP，试图通过发明一个新概念"代理"来解决这个长列表问题，该代理执行寻址、路由和排队。这导致了一个客户端/服务器协议或一组 API，它们位于某个未记录的协议之上，允许应用程序与此代理对话。代理在降低大型网络的复杂性方面是一件极好的事情。但向 Zookeeper 这样的产品添加基于代理的消息传递会使其变得更糟，而不是更好。这将意味着添加一个额外的大盒子，以及一个新的单点故障。代理很快成为瓶颈和需要管理的新风险。如果软件支持它，我们可以添加第二、第三和第四个代理，并制定一些故障转移方案。人们这样做。它创建了更多的移动部件、更多的复杂性和更多会损坏的东西。

因此，中小型应用程序开发人员被困住了。要么他们避免网络编程，制作不会扩展的单体应用程序。要么他们跳入网络编程，制作脆弱、复杂的应用程序，难以维护。要么他们押注消息传递产品，最终得到可扩展的应用程序，依赖于昂贵、易碎的技术。一直没有真正好的选择，这也许就是为什么消息传递在很大程度上停留在上个世纪，并激起强烈情绪的原因：用户的负面情绪，那些销售支持和许可证的人的欢乐喜悦。

我们需要的是做消息传递工作的东西，但以一种如此简单和廉价的方式，它可以在任何应用程序中工作，几乎零成本。它应该是一个你只需链接的库，没有任何其他依赖项。没有额外的移动部件，因此没有额外的风险。它应该可以在任何操作系统上运行，并与任何编程语言一起工作。

这就是 ZeroMQ：一个高效的、可嵌入的库，解决了应用程序需要在网络中变得良好弹性的大部分问题，成本很低。

具体来说：

* 它在后台线程中异步处理 I/O。这些使用无锁数据结构与应用线程通信，因此并发 ZeroMQ 应用程序不需要锁、信号量或其他等待状态。

* 组件可以动态地来来去去，ZeroMQ 将自动重新连接。这意味着你可以按任何顺序启动组件。你可以创建"面向服务的架构"（SOA），其中服务可以在任何时候加入和离开网络。

* 它在需要时自动排队消息。它智能地执行此操作，在排队之前尽可能将消息推近接收者。

* 它有处理过满队列（称为"高水位标记"）的方法。当队列满时，ZeroMQ 会自动阻止发送者，或丢弃消息，取决于你正在做的消息传递类型（所谓的"模式"）。

* 它让你的应用程序通过任意传输相互通信：TCP、多播、进程内、进程间。你不需要更改代码即可使用不同的传输。

* 它使用取决于消息传递模式的不同策略安全地处理慢/阻塞的读取器。

* 它让你使用各种模式路由消息，如请求 - 回复和发布 - 订阅。这些模式是你如何创建拓扑、网络结构的方法。

* 它让你用单个调用创建代理来排队、转发或捕获消息。代理可以降低网络的互连复杂性。

* 它完全按照发送的方式传递整个消息，使用简单的线框。如果你写一条 10k 的消息，你将收到一条 10k 的消息。

* 它不对消息施加任何格式。它们是从零到千兆字节大的二进制大对象。当你想要表示数据时，你选择一些其他产品在上面，如 msgpack、Google 的协议缓冲区等。

* 它智能地处理网络错误，通过在有意义的情况下自动重试。

* 它减少你的碳足迹。用更少的 CPU 做更多的事情意味着你的盒子使用更少的电力，你可以让你的旧盒子使用时间更长。Al Gore 会喜欢 ZeroMQ。

实际上，ZeroMQ 做得远不止这些。它对你如何开发网络能力的应用程序有一种颠覆性的影响。表面上，它是一个受套接字启发的 API，你可以在其上执行<tt>[zmq_recv()](http://api.zeromq.org/master:zmq_recv)</tt>和<tt>[zmq_send()](http://api.zeromq.org/master:zmq_send)</tt>。但消息处理迅速成为中心循环，你的应用程序很快分解为一组消息处理任务。它是优雅和自然的。而且它扩展：这些任务中的每一个都映射到一个节点，节点通过任意传输相互通信。一个进程中的两个节点（节点是一个线程），一个盒子上的两个节点（节点是一个进程），或一个网络上的两个节点（节点是一个盒子）——都是一样的，无需更改应用程序代码。

## 套接字可扩展性 {#Socket-Scalability}

让我们看看 ZeroMQ 的可扩展性。这里是一个 shell 脚本，它启动天气服务器，然后并行启动一堆客户端：

```
wuserver &
wuclient 12345 &
wuclient 23456 &
wuclient 34567 &
wuclient 45678 &
wuclient 56789 &
```

当客户端运行时，我们使用<tt>top</tt>命令查看活动进程，我们看到类似这样的东西（在一个 4 核盒子上）：

```
PID  USER  PR  NI  VIRT  RES  SHR S %CPU %MEM   TIME+  COMMAND
7136  ph   20   0 1040m 959m 1156 R  157 12.0 16:25.47 wuserver
7966  ph   20   0 98608 1804 1372 S   33  0.0  0:03.94 wuclient
7963  ph   20   0 33116 1748 1372 S   14  0.0  0:00.76 wuclient
7965  ph   20   0 33116 1784 1372 S    6  0.0  0:00.47 wuclient
7964  ph   20   0 33116 1788 1372 S    5  0.0  0:00.25 wuclient
7967  ph   20   0 33072 1740 1372 S    5  0.0  0:00.35 wuclient
```

让我们思考一下这里发生了什么。天气服务器有一个套接字，但在这里我们让它并行向五个客户端发送数据。我们可以有数千个并发客户端。服务器应用程序看不到它们，不与它们直接对话。因此，ZeroMQ 套接字就像一个小的服务器，默默地接受客户端请求，并尽可能快地将数据推送给它们，以网络能够处理的速度。它是一个多线程服务器，从你的 CPU 中挤出更多的汁液。

## 从 ZeroMQ v2.2 升级到 ZeroMQ v3.2 {#Upgrading-from-ZeroMQ-v-to-ZeroMQ-v}

### 兼容的更改 {#Compatible-Changes}

这些更改不会直接影响现有的应用程序代码：

* 发布 - 订阅过滤现在从订阅者端转移到发布者端。这在许多发布 - 订阅用例中显著提高了性能。你可以安全地混合 v3.2 和 v2.1/v2.2 发布者和订阅者。

* ZeroMQ v3.2 有许多新的 API 方法（<tt>[zmq_disconnect()](http://api.zeromq.org/master:zmq_disconnect)</tt>、<tt>[zmq_unbind()](http://api.zeromq.org/master:zmq_unbind)</tt>、<tt>[zmq_monitor()](http://api.zeromq.org/master:zmq_monitor)</tt>、<tt>[zmq_ctx_set()](http://api.zeromq.org/master:zmq_ctx_set)</tt>等）

### 不兼容的更改 {#Incompatible-Changes}

这些是对应用程序和语言绑定的主要影响领域：

* 更改的发送/接收方法：<tt>[zmq_send()](http://api.zeromq.org/master:zmq_send)</tt>和<tt>[zmq_recv()](http://api.zeromq.org/master:zmq_recv)</tt>有不同、更简单的接口，旧功能现在由<tt>[zmq_msg_send()](http://api.zeromq.org/master:zmq_msg_send)</tt>和<tt>[zmq_msg_recv()](http://api.zeromq.org/master:zmq_msg_recv)</tt>提供。症状：编译错误。解决方案：修复你的代码。

* 这两种方法在成功时返回正值，在错误时返回 -1。在 v2.x 中，它们在成功时总是返回零。症状：事情实际上运行良好时的明显错误。解决方案：严格测试返回码=-1，而不是非零。

* <tt>[zmq_poll()](http://api.zeromq.org/master:zmq_poll)</tt>现在等待毫秒，而不是微秒。症状：应用程序停止响应（实际上响应速度慢了 1000 倍）。解决方案：在所有<tt>zmq_poll</tt>调用中使用下面定义的<tt>ZMQ_POLL_MSEC</tt>宏。

* <tt>ZMQ_NOBLOCK</tt>现在被称为<tt>ZMQ_DONTWAIT</tt>。症状：<tt>ZMQ_NOBLOCK</tt>宏上的编译失败。

* <tt>ZMQ_HWM</tt>套接字选项现在被拆分为<tt>ZMQ_SNDHWM</tt>和<tt>ZMQ_RCVHWM</tt>。症状：<tt>ZMQ_HWM</tt>宏上的编译失败。

* 大多数但不是所有<tt>[zmq_getsockopt()](http://api.zeromq.org/master:zmq_getsockopt)</tt>选项现在都是整数值。症状：<tt>zmq_setsockopt</tt>和<tt>zmq_getsockopt</tt>上的运行时错误返回。

* <tt>ZMQ_SWAP</tt>选项已被删除。症状：<tt>ZMQ_SWAP</tt>上的编译失败。解决方案：重新设计使用此功能的任何代码。

### 建议的 Shim 宏 {#Suggested-Shim-Macros}

对于想要在 v2.x 和 v3.2 上运行的应用程序，如语言绑定，我们的建议是尽可能模拟 v3.2。以下是 C 宏定义，帮助你的 C/C++ 代码在两个版本上工作（来自 [CZMQ](http://czmq.zeromq.org)）：

{{< fragment name="upgrade-shim" >}}
#ifndef ZMQ_DONTWAIT
#   define ZMQ_DONTWAIT     ZMQ_NOBLOCK
#endif
#if ZMQ_VERSION_MAJOR == 2
#   define zmq_msg_send(msg,sock,opt) zmq_send (sock, msg, opt)
#   define zmq_msg_recv(msg,sock,opt) zmq_recv (sock, msg, opt)
#   define zmq_ctx_destroy(context) zmq_term(context)
#   define ZMQ_POLL_MSEC    1000        //  zmq_poll is usec
#   define ZMQ_SNDHWM ZMQ_HWM
#   define ZMQ_RCVHWM ZMQ_HWM
#elif ZMQ_VERSION_MAJOR == 3
#   define ZMQ_POLL_MSEC    1           //  zmq_poll is msec
#endif
{{< /fragment >}}

## 警告：不稳定的范式！ {#Warning-Unstable-Paradigms}

传统网络编程建立在一般假设之上，即一个套接字与一个连接、一个对等体对话。有多播协议，但这些是异国情调的。当我们假设"一个套接字=一个连接"时，我们以某些方式扩展我们的架构。我们创建逻辑线程，其中每个线程与一个套接字、一个对等体一起工作。我们在这些线程中放置智能和状态。

在 ZeroMQ 宇宙中，套接门是通往快速小后台通信引擎的门道，这些引擎自动为你管理一整套连接。你看不到、无法使用、打开、关闭或附加状态到这些连接。无论你使用阻塞发送或接收，还是轮询，你只能与套接字对话，而不是它为你管理的连接。连接是私有的和不可见的，这是 ZeroMQ 可扩展性的关键。

这是因为你的代码，与套接字对话，然后可以处理跨任何网络协议的任意数量的连接，无需更改。坐在 ZeroMQ 中的消息传递模式比坐在应用程序代码中的消息传递模式扩展得更便宜。

所以一般假设不再适用。当你阅读代码示例时，你的大脑会试图将它们映射到你已知的东西。你会读到"套接字"并想"啊，这代表了与另一个节点的连接"。这是错误的。你会读到"线程"，你的大脑会再次想"啊，线程代表了与另一个节点的连接"，你的大脑会再次错误。

如果你是第一次阅读本指南，意识到在你真正编写 ZeroMQ 代码一两天（也许三四天）之前，你可能会感到困惑，特别是 ZeroMQ 为你做得多么简单，你可能会试图将那个一般假设强加给 ZeroMQ，它不会工作。然后你会体验到你的启蒙和信任时刻，那个*zap-pow-kaboom*顿悟范式转变的时刻，当一切都变得清晰时。
