# 使用 ZeroMQ 的高级架构

在大规模使用 ZeroMQ 时产生的一个效果是，由于我们能够比以往更快地构建分布式架构，我们软件工程流程的局限性变得更加明显。缓慢移动中的错误往往更难被发现（或者说，更容易被合理化）。

我在向工程师团队教授 ZeroMQ 时的经验是，仅仅解释 ZeroMQ 的工作原理然后就期望他们开始构建成功的产品是远远不够的。像任何消除摩擦的技术一样，ZeroMQ 为大错误打开了大门。如果 ZeroMQ 是分布式软件开发中的 ACME 火箭推进鞋，那么我们很多人就像威利狼一样，以全速撞上众所周知的沙漠悬崖。

## 面向消息的模式用于弹性设计

我将介绍面向消息的模式用于弹性设计（MOPED），这是一个用于 ZeroMQ 架构的软件工程模式。它要么是"MOPED"，要么是"BIKE"，即反向缩略词诱导的动力学效应。这是"BICICLE"的简称，即反向缩略词膨胀的我不在乎效应。在生活中，人们学会了选择最不尴尬的那个。

MOPED 的目标是定义一个流程，通过它我们可以为一个新的分布式应用程序提供一个粗略的用例，并在不到一周的时间内从"Hello World"到完全工作的原型，使用任何语言。

我们可以将其转化为五个实际步骤：

* 步骤 1：内化 ZeroMQ 语义
* 步骤 2：绘制粗略架构
* 步骤 3：决定契约
* 步骤 4：制作最小端到端解决方案
* 步骤 5：解决一个问题并重复

### 步骤 1：内化语义

你必须学习并消化 ZeroMQ 的"语言"，即套接字模式及其工作原理。学习语言的唯一方法就是使用它。没有避免这种投资的方法，没有你可以在睡觉时播放的磁带，没有你可以插入以神奇地变得更聪明的芯片。从头开始阅读这本书，用你喜欢的语言完成代码示例，理解发生了什么，（最重要的是）自己写一些示例，然后把它们扔掉。

### 步骤 2：绘制粗略架构

根据我的经验，能够绘制架构的核心是至关重要的。它有助于他人理解你的想法，也有助于你自己思考。确实没有比使用白板向同事解释你的想法更好的设计好架构的方法了。

你不需要把它做对，也不需要把它做完整。你需要做的是将架构分解成有意义的片段。软件架构（与建造桥梁相比）的好处在于，如果已经将它们隔离，你真的可以廉价地替换整个层。

### 步骤 3：决定契约

一个好的软件架构依赖于契约，它们越明确，事情就扩展得越好。你不在乎//如何//发生事情；你只关心结果。如果我发送一封电子邮件，我不在乎它如何到达目的地，只要契约得到尊重。电子邮件契约是：它在几分钟内到达，没有人修改它，它不会丢失。

那么分布式系统中的契约是什么？根据我的经验，有两种类型的契约：

* 客户端应用程序的 API。记住心理元素。API 需要尽可能//简单//、//一致//和//熟悉//。
* 连接片段的协议。它听起来像火箭科学，但它实际上只是一个简单的技巧，ZeroMQ 使它变得特别容易。

### 步骤 4：编写最小端到端解决方案

目标是尽可能快地测试整体架构。制作调用 API 的骨架应用程序，以及实现每个协议两侧的骨架协议栈。你希望尽快获得一个端到端的"Hello World"。你希望能够在你编写代码时测试代码，以便你可以剔除错误的假设和你不可避免会犯的错误。

### 步骤 5：解决一个问题并重复

你现在处于问题驱动开发的快乐循环中，你可以开始解决实际问题而不是添加功能。编写每个陈述明确问题并提出解决方案的问题。在你设计 API 时，请记住你对名称、一致性和行为的标准。

## 非协议

### 没有山羊的协议

当这个人想到协议时，这个人会想到委员会多年来编写的大量文件。这个人想到了 IETF、W3C、ISO、Oasis、监管捕获、FRAND 专利许可纠纷，不久之后，这个人就想到了退休到玻利维亚北部山区的一个可爱的小农场，那里唯一其他不必要的固执的生物是山羊在咀嚼咖啡植物。

现在，ZeroMQ 似乎确实提供了一个活的、成功的协议抽象层，其"我们将在随机传输上携带多部分消息"的工作方式。由于 ZeroMQ 默默地处理框架、连接和路由，因此在 ZeroMQ 之上编写完整的协议规范非常容易。

大约在 2007 年中期，我启动了数字标准组织，以定义新的更简单的方法来生成小标准、协议和规范。2010 年，我们开始称这种小规范为//非协议//，这意味着"没有山羊的协议"。

### 契约很难

编写契约也许是大型架构中最困难的部分。使用非协议，我们尽可能多地消除不必要的摩擦。剩下的仍然是一组需要解决的难题。一个好的契约（无论是 API、协议还是租赁协议）必须是简单、明确、技术上合理且易于执行的。

我将尝试总结我作为协议编写者的经验：

* 从简单开始，逐步开发你的规范。不要解决你面前没有的问题。
* 使用非常清晰和一致的语言。协议通常可以分解为命令和字段；为这些实体使用清晰简短的名称。
* 尽量避免发明概念。尽可能从现有规范中重用任何东西。
* 制作//没有//你无法证明有即时需求的东西。你的规范解决问题；它不提供功能。
* 在构建过程中实现你的协议//，这样你就知道每个选择的技术后果。
* 在你构建规范的过程中，在其他人身上测试你的规范。
* 快速一致地交叉测试，将其他人的客户端与你的服务器对调，反之亦然。
* 准备好根据需要扔掉并重新开始。为此做好计划，通过分层你的架构。
* 只使用独立于编程语言和操作系统的构造。
* 分层解决大型问题，使每一层都成为独立的规范。

最重要的是，//把它写下来//。代码不是规范。书面规范的重点是，无论它多么薄弱，它都可以系统地改进。

### 如何编写非协议

当你开始编写非协议规范文档时，坚持一致的结构，以便你的读者知道会发生什么。这是我使用的结构：

* 封面部分：包含 1 行摘要、规范的 URL、正式名称、版本、责任人。
* 文本的许可证：对于公共规范绝对需要。
* 变更流程：即，作为读者我如何修复规范中的问题？
* 语言的使用：必须、可能、应该等，参考 RFC 2119。
* 成熟度指标：这是实验性的、草案、稳定、遗留还是退役？
* 协议的目标：它试图解决什么问题？
* 正式语法：防止由于文本的不同解释而引起的争论。
* 技术解释：每条消息的语义、错误处理等。
* 安全讨论：明确协议的安全性。
* 参考资料：其他文档、协议等。

### 为什么对公共规范使用 GPLv3？

你选择的许可证对于公共规范特别重要。传统上，协议是在自定义许可证下发布的，作者拥有文本，禁止派生作品。这听起来很棒（毕竟，谁想看到协议分叉？），但实际上风险很高。

让我用更短的词来解释这一点。想象一下，iMatix 今天写了一个非常惊人且流行的协议。我们发布规范，许多人实现它。这些实现快速而棒，像啤酒一样免费。它们开始威胁现有的业务。他们昂贵的商业产品速度较慢，无法竞争。所以有一天，他们来到我们在韩国梅塘洞的 iMatix 办公室，提出收购我们公司。由于我们在寿司和啤酒上花费了大量资金，我们感激地接受了。新所有者带着邪恶的笑声停止改进公共版本，关闭规范，并添加专利扩展。他们的新产品支持这个新协议版本，但开源版本在法律上被阻止这样做。该公司接管了整个市场，竞争结束。

当你为开源项目做出贡献时，你真的想知道你的辛勤工作不会被闭源竞争对手用来对付你。这就是为什么 GPL 击败了"更宽松"的 BSD/MIT/X11 许可证，适用于大多数贡献者。

### 使用 ABNF

我在编写协议规范时的建议是学习并使用正式语法。这只是比允许他人解释你的意思更少的麻烦，然后从不可避免的错误假设中恢复。你的语法的目标是其他人，工程师，而不是编译器。

我最喜欢的语法是 ABNF，如 RFC 2234 所定义，因为它可能是最简单且最广泛使用的定义双向通信协议的正式语言。大多数 IETF 规范都使用 ABNF，这是一个很好的公司。

我将给出一个 30 秒的速成课程，教你如何编写 ABNF。它可能会让你想起正则表达式。你将语法编写为规则。每条规则都采用"名称 = 元素"的形式。元素可以是另一条规则或预定义的终端，如 CRLF、OCTET 或数字。

要定义替代元素，用斜杠分隔。要定义重复，使用星号。要分组元素，使用括号。阅读 RFC，因为它不直观。

我不确定这个扩展是否合适，但我然后用"C:"和"S:"前缀元素，以指示它们是来自客户端还是服务器。

以下是一个名为 NOM 的非协议的一段 ABNF：

```
nom-protocol    = open-peering *use-peering

open-peering    = C:OHAI ( S:OHAI-OK / S:WTF )

use-peering     = C:ICANHAZ
                / S:CHEEZBURGER
                / C:HUGZ S:HUGZ-OK
                / S:HUGZ C:HUGZ-OK
```

### 便宜或糟糕模式

我几十年来编写大大小小的协议学到的一个普遍教训是，我称之为//便宜或糟糕//模式：你通常可以将你的工作分成两个方面或层，并分别解决这些——一个使用"便宜"方法，另一个使用"糟糕"方法。

使便宜或糟糕奏效的关键洞察是意识到许多协议混合了用于控制的低容量聊天部分和用于数据的高容量异步部分。例如，HTTP 有一个聊天对话来验证和获取页面，还有一个异步对话来流式传输数据。FTP 实际上在两个端口上分割了这一点；一个端口用于控制，一个端口用于数据。

协议设计者如果不将控制与数据分开，往往会做出可怕的协议，因为这两种情况下的权衡几乎完全相反。对控制完美的东西对数据来说是糟糕的，对数据理想的东西对控制来说根本不起作用。

* 控制对话持续时间短，涉及的消息很少。数据流可能持续数小时或数天，涉及数十亿条消息。
* 控制对话是所有"正常"错误发生的地方。相比之下，数据流期间发生的任何错误都是异常的。
* 控制对话是随着时间的推移而发生变化的地方。数据流随着时间的推移几乎不应该发生变化。
* 控制对话本质上是一个同步请求/回复对话。数据流本质上是一个单向异步流。

### 错误处理

使用便宜或糟糕会使错误处理变得相当简单。你有两种命令和两种发出错误信号的方法：

* 同步控制命令：错误是正常的：每个请求都有一个响应，要么是 OK，要么是错误响应。
* 异步数据命令：错误是异常的：坏命令要么被静默丢弃，要么导致整个连接关闭。

## 序列化你的数据

当我们开始设计协议时，我们面临的第一个问题之一是我们如何在线上编码数据。没有通用的答案。有半打不同的方法来序列化数据，每种方法都有优点和缺点。

### 抽象级别

在考虑如何将数据放到线上之前，值得问一下我们实际上想要在应用程序之间交换什么数据。如果我们不使用任何抽象，我们实际上会序列化和反序列化我们的内部状态。也就是说，我们用来实现功能的对象和结构。

然而，将内部状态放到线上是一个非常糟糕的主意。这就像在 API 中暴露内部状态一样。当你这样做时，你会将你的实现决策硬编码到你的协议中。你还会产生比你需要的复杂得多的协议。

一个好的协议或 API 抽象封装了自然的使用模式，并给它们起了可预测和规则的名称和属性。它为主流情况选择了合理的默认值，以便可以最小限度地指定主流情况。它旨在为简单情况提供简单性，为罕见的复杂情况提供表现力。

### ZeroMQ 框架

ZeroMQ 应用程序中最简单且最广泛使用的序列化格式是 ZeroMQ 自己的多部分框架。例如，这是 Majordomo 协议定义请求的方式：

```
Frame 0: Empty frame
Frame 1: "MDPW01" (six bytes, representing MDP/Worker v0.1)
Frame 2: 0x02 (one byte, representing REQUEST)
Frame 3: Client address (envelope stack)
Frame 4: Empty (zero bytes, envelope delimiter)
Frames 5+: Request body (opaque binary)
```

在代码中读取和写入这很容易，但这是控制流的一个经典示例（整个 MDP 实际上是一个聊天请求 - 回复协议）。当我们推出第二个版本来改进 MDP 时，我们不得不改变这个框架。太好了，我们破坏了所有现有的实现！

向后兼容性很难，但将 ZeroMQ 框架用于控制流没有帮助。以下是我如果遵循自己的建议应该如何设计这个协议：它分为便宜部分和糟糕部分，并使用 ZeroMQ 框架来分隔这些：

```
Frame 0: "MDP/2.0" for protocol name and version
Frame 1: command header
Frame 2: command body
```

### 序列化语言

序列化语言有自己的时尚。XML 曾经很受欢迎，然后它变得过于工程化，然后它落入了"企业信息架构师"的手中，从此就再也没有人见过它活着。

JSON 从 JavaScript 世界中跳出来，作为一种快速而肮脏的"我宁愿辞职也不愿在这里使用 XML"的方式，将数据扔到线上，然后再把它拿回来。JSON 只是以 JavaScript 源代码的形式表达的最小 XML。

以下是在便宜协议中使用 JSON 的简单示例：

```json
"protocol": {
    "name": "MTL",
    "version": 1
},
"virtual-host": "test-env"
```

同样的数据在 XML 中将是（XML 强制我们发明一个顶级实体）：

```xml
<command>
    <protocol name = "MTL" version = "1" />
    <virtual-host>test-env</virtual-host>
</command>
```

这里使用普通的 HTTP 样式标头：

```
Protocol: MTL/1.0
Virtual-host: test-env
```

只要你不用验证解析器、模式和其他"相信我们，这都是为你好"的废话过度使用，这些都是相当等价的。

### 序列化库

MessagePack 网站说：

> 它就像 JSON，但快速而小。MessagePack 是一种高效的二进制序列化格式。它让你像 JSON 一样在多种语言之间交换数据，但它更快更小。

我将提出一个可能不受欢迎的说法，即"快速和小"是解决非问题的功能。据我所知，序列化库解决的唯一真正问题是记录消息契约的需求，以及实际将数据序列化到线上和从线上反序列化数据的需求。

让我们从揭穿"快速和小"开始。它基于两部分论证。首先，使你的消息更小并减少编码和解码的 CPU 成本将对你的应用程序性能产生重大影响。其次，这在整个过程中都是同等有效的。

但大多数实际应用程序往往属于两类之一。要么序列化的速度和编码的大小与其他成本（如数据库访问或应用程序代码性能）相比微不足道。或者，网络性能确实至关重要，然后所有重大成本都发生在少数特定消息类型中。

因此，全面追求"快速和小"是一种错误的优化。你既不会为不频繁的控制流获得简单的灵活性，也不会为高容量数据流获得残酷的效率。更糟糕的是，所有消息在某些方面都是平等的假设可能会破坏你的协议设计。

### 手写二进制序列化

从本书的前面部分你会了解到，我首选的系统编程语言是 C（升级到 C99，带有构造函数/析构函数 API 模型和通用容器）。我喜欢这种现代化的 C 语言有两个原因。首先，我太弱智了，无法学习像 C++ 这样的大语言。生活似乎充满了更有趣的事情需要理解。其次，我发现这种特定级别的手动控制让我能够更快地产生更好的结果。

当你真正、真正关心序列化的速度和/或结果的大小时（这些往往是相互矛盾的），你需要手写的二进制序列化。换句话说，让我们为讨厌先生鼓掌！

你编写高效的糟糕编码器/解码器（编解码器）的基本过程是：

* 构建代表性数据集和可以对你的编解码器进行压力测试的测试应用程序。
* 编写编解码器的第一个愚蠢版本。
* 测试、测量、改进，重复直到你用完时间和/或金钱。

以下是我们用来改进编解码器的一些技术：

* //使用分析器。// 在你对函数计数和每个函数的 CPU 成本进行分析之前，根本无法知道你的代码在做什么。当你找到热点时，修复它们。
* //消除内存分配。// 堆在现代 Linux 内核上非常快，但它仍然是大多数天真编解码器中的瓶颈。在较旧的内核上，堆可能慢得令人痛心。尽可能使用局部变量（堆栈）而不是堆。
* //在不同的平台上使用不同的编译器和编译器选项进行测试。// 除了堆之外，还有许多其他差异。你需要了解主要的差异，并为它们留出余地。
* //使用状态来更好地压缩。// 如果你关心编解码器的性能，你几乎肯定在多次发送相同类型的数据。实例之间会存在冗余。你可以检测到这些，并利用这一点进行压缩。
* //了解你的数据。// 最好的压缩技术（就紧凑性的 CPU 成本而言）需要了解数据。例如，用于压缩单词列表、视频和股票市场数据流的技术都是不同的。
* //准备好打破规则。// 你真的需要以大端网络字节顺序编码整数吗？x86 和 ARM 几乎占据了所有现代 CPU，但都使用小端。

大多数软件工程师知道的代码生成器都带有单个硬编码模型。例如，Ragel"从正则语言编译可执行有限状态机"，即，Ragel 的模型是正则语言。这肯定适用于一组好的问题，但它远非通用。

你如何在 Ragel 中描述 API？或者项目生成文件？或者像我们在设计 Binary Star 模式时使用的有限状态机？

你需要一些如何制作好模型的经验，你需要一种技术，使构建自定义代码生成器变得便宜。像 Perl 和 Python 这样的脚本语言是一个不错的选择。然而，我们实际上专门为这个目的构建了 GSL，这就是我更喜欢的。

当我们编写 GSL 模型时，我们可以使用任何我们喜欢的语义，换句话说，我们可以当场发明特定领域的语言。我将发明几个——看看你是否能猜出它们代表什么：

所以对于这个练习，我们的领域语言，我们的模型，由包含"消息"的"类"组成，这些消息包含各种类型的"字段"。这是故意熟悉的。

以下是 MDP 客户端协议：

```xml
<class name = "mdp_client">
    MDP/Client
    <header>
        <field name = "empty" type = "string" value = ""
            >Empty frame</field>
        <field name = "protocol" type = "string" value = "MDPC01"
            >Protocol identifier</field>
    </header>
    <message name = "request">
        Client request to broker
        <field name = "service" type = "string">Service name</field>
        <field name = "body" type = "frame">Request body</field>
    </message>
    <message name = "reply">
        Response back to client
        <field name = "service" type = "string">Service name</field>
        <field name = "body" type = "frame">Response body</field>
    </message>
</class>
```

GSL 使用 XML 作为其建模语言。XML 有一个糟糕的声誉，因为它被拖入了太多的企业下水道，闻起来不再香甜，但它有一些强大的优点，只要你保持简单。

以下是一个用 GSL 编写的简短 IDL 生成器，它将我们的协议模型转换为文档：

```
.#  Trivial IDL generator (specs.gsl)
.#
.output "$(class.name).md"
## The $(string.trim (class.?''):left) Protocol
.for message
.   frames = count (class->header.field) + count (field)

A $(message.NAME) command consists of a multipart message of $(frames)
frames:

.   for class->header.field
.       if name = "id"
* Frame $(item ()): 0x$(message.id:%02x) (1 byte, $(message.NAME))
.       else
* Frame $(item ()): "$(value:)" ($(string.length ("$(value)")) \
bytes, $(field.:))
.       endif
.   endfor
.   index = count (class->header.field) + 1
.   for field
* Frame $(index): $(field.?'') \
.       if type = "string"
(printable string)
.       elsif type = "frame"
(opaque binary)
.           index += 1
.       else
.           echo "E: unknown field type: $(type)"
.       endif
.       index += 1
.   endfor
.endfor
```

XML 模型和这个脚本在子目录 examples/models 中。为了进行代码生成，我给出了这个命令：

```
gsl -script:specs mdp_client.xml mdp_worker.xml
```

```

```

这给了我们 mdp_client 和 mdp_worker 类。实际上，MDP 非常简单，几乎不值得编写代码生成器的努力。利润来自于我们想要更改协议时（我们对独立 Majordomo 项目这样做了）。你修改协议，运行命令，然后弹出更多完美的代码。

我现在将解释面向模型的代码生成的优缺点。权力不是免费的，我们业务中最大的陷阱之一是能够凭空发明概念。GSL 使这变得特别容易，因此它可能是一个同样危险的工具。

不要发明概念。设计者的工作是消除问题，而不是添加功能。

首先，我将列出面向模型的代码生成的优点：

* 你可以创建接近完美的抽象，映射到你的现实世界。
* 你可以快速廉价地开发这些完美模型。
* 你可以生成任何文本输出。从单个模型中，你可以创建文档、任何语言的代码、测试工具——几乎任何你能想到的输出。
* 你可以生成完美输出，因为改进你的代码生成器到你想要的任何级别都很便宜。
* 你得到一个结合了规范和语义的单一来源。
* 你可以利用一个小团队来大规模扩展。在 iMatix，我们从大约 85K 行的输入模型中生成了百万行的 OpenAMQ 消息传递产品，包括代码生成脚本本身。

现在让我们看看缺点：

* 你为你的项目添加了工具依赖关系。
* 你可能会得意忘形，为了纯粹的创造乐趣而创建模型。
* 你可能会疏远新来者，他们会从你的工作中看到"奇怪的东西"。
* 你可能会给别人一个强烈的借口，不投资于你的项目。

因此，如果你确实使用 GSL，并且想要围绕你的工作创建开放社区，这是我的建议：

* 只在你否则会手工编写乏味代码的地方使用它。
* 设计人们期望看到的自然模型。
* 首先手工编写代码，这样你就知道要生成什么。
* 不要过度使用。保持简单！不要太元！！
* 逐步引入项目。
* 将生成的代码放入你的存储库中。

我们已经在 ZeroMQ 周围的一些项目中使用 GSL。例如，高级 C 绑定 CZMQ 使用 GSL 来生成套接字选项类（zsockopt）。一个 300 行的代码生成器将 78 行的 XML 模型转换为 1,500 行的完美但非常无聊的代码。这是一个很好的胜利。

## 传输文件

让我们从说教中休息一下，回到我们的初恋和做这一切的原因：代码。

"如何发送文件？"是 ZeroMQ 邮件列表上的一个常见问题。这不应该让人感到惊讶，因为文件传输也许是最古老、最明显的消息传递类型。通过网络发送文件除了惹恼版权卡特尔之外，还有很多用例。ZeroMQ 在开箱即用的情况下非常擅长发送事件和任务，但在发送文件方面就不那么擅长了。

我已经承诺了一两年要写一个适当的解释。这里有一条免费的信息来照亮你的早晨："proper"这个词来自古法语 propre，意思是"干净"。黑暗时代的英国平民不熟悉热水和肥皂，把这个词改成了"外国的"或"上层阶级"的意思，如"那是合适的食物！"，但后来这个词只是变成了"真正的"意思，如"你给我们带来了合适的混乱！"

所以，文件传输。你不能只是随机挑选一个文件，蒙住它的眼睛，然后把它整个塞进一条消息里，有几个原因。最明显的原因是，尽管 RAM 大小几十年来坚定不移地增长（我们这些老前辈中谁不深情地记得攒钱买那张 1024 字节的内存扩展卡？！），磁盘大小却顽固地保持更大。

即使我们可以用一条指令发送文件（比如说，使用像 sendfile 这样的系统调用），我们也会遇到现实，网络不是无限快，也不是完全可靠的。在缓慢、不可靠的网络（WiFi，有人吗？）上尝试上传一个大文件几次后，你会意识到一个适当的文件传输协议需要一种从故障中恢复的方法。也就是说，它需要一种方法来发送文件的尚未收到的部分。

最后，在所有这些之后，如果你构建一个适当的文件服务器，你会注意到，简单地向大量客户端发送大量数据会产生我们喜欢用技术术语称之为"由于设计不良的应用程序吃掉了所有可用的堆内存，服务器肚皮朝天"的情况。一个适当的文件传输协议需要注意内存使用。

我们将逐一妥善解决这些问题，希望最终能让我们得到一个运行在 ZeroMQ 上的良好且适当的文件传输协议。

首先，让我们生成一个带有随机数据的 1GB 测试文件：

```bash
dd if=/dev/urandom of=testdata bs=1M count=1024
```

这足够大，当我们有很多客户端同时请求同一个文件时，它会带来麻烦，而且在许多机器上，1GB 将太大而无法在内存中分配。作为基本参考，让我们测量一下将这个文件从磁盘复制回磁盘需要多长时间。这将告诉我们我们的文件传输协议增加了多少开销（包括网络成本）：

```bash
$ time cp testdata testdata2

real    0m7.143s
user    0m0.012s
sys     0m1.188s
```

以下是第一个代码版本，客户端请求测试数据，服务器只是不间断地发送它，作为一系列消息，其中每条消息包含一个块：

它非常简单，但我们已经遇到了一个问题：如果我们向 ROUTER 套接字发送太多数据，我们可以很容易地溢出它。简单但愚蠢的解决方案是在套接字上放置一个无限的高水位标记。这是愚蠢的，因为我们现在对耗尽服务器内存没有任何保护。然而，如果没有无限的 HWM，我们就有丢失大文件块的风险。

试试这个：将 HWM 设置为 1,000（在 ZeroMQ v3.x 中这是默认的），然后将块大小减少到 100K，这样我们一次发送 10K 块。运行测试，你会看到它永远不会完成。

我们必须预先控制服务器发送的数据量。它发送的数据量超过网络可以处理的数据量是没有任何意义的。让我们尝试一次发送一个块。在这个协议版本中，客户端将明确地说，"给我块 N"，服务器将从磁盘获取该特定块并发送它。

以下是改进的第二个模型，客户端一次请求一个块，服务器只为它从客户端获得的每个请求发送一个块：

它现在慢得多，因为客户端和服务器之间的来回聊天。我们为每个请求 - 回复往返支付大约 300 微秒的费用，在本地环回连接上（客户端和服务器在同一个盒子上）。听起来不多，但它很快就会累加：

```bash
$ time ./fileio1
4296 chunks received, 1073741824 bytes

real    0m0.669s
user    0m0.056s
sys     0m1.048s

$ time ./fileio2
4295 chunks received, 1073741824 bytes

real    0m2.389s
user    0m0.312s
sys     0m2.136s
```

这里有两个宝贵的教训。首先，虽然请求 - 回复很容易，但对于高容量数据流来说也太慢了。为每个块支付 300 微秒一次是可以的。为每个单独的块支付它是不可接受的，特别是在实际网络上，延迟可能比这高 1,000 倍。

第二点是我在之前说过的，但会重复：在 ZeroMQ 上实验、测量和改进协议是非常容易的。当某物的成本大幅下降时，你可以负担得起更多。学会隔离开发和证明你的协议：我见过团队浪费时间试图改进设计不佳的协议，这些协议在应用程序中嵌入得太深，无法轻松测试或修复。

我们的模型二文件传输协议还不错，除了性能：

* 它完全消除了内存耗尽的风险。为了证明这一点，我们在发送方和接收方都将高水位标记设置为 1。
* 它让客户端选择块大小，这是有用的，因为如果要对块大小进行任何调整，以适应网络条件、文件类型，或进一步减少内存消耗，应该是客户端在进行此操作。
* 它为我们提供了完全可重启的文件传输。
* 它允许客户端随时取消文件传输。

如果我们不必为每个块发出请求，它就是一个可用的协议。我们需要一种方法让服务器在无需等待客户端请求或确认每个块的情况下发送多个块。我们有哪些选择？

* 服务器可以一次发送 10 个块，然后等待单个确认。这完全就像将块大小乘以 10，所以它是没有意义的。

* 服务器可以在没有任何客户端聊天的情况下发送块，但在每次发送之间稍有延迟，这样它只会以网络可以处理的速度发送块。这需要服务器知道网络层发生了什么，这听起来像是一项艰苦的工作。

* 服务器可以尝试监视发送队列，即，看看它有多满，并且只在队列不满时发送。嗯，ZeroMQ 不允许这样做，因为它不起作用。

除了复杂和各种各样的不愉快之外，这些选项甚至都不会起作用。我们需要一种方法让客户端异步且在后台告诉服务器，它已经准备好了更多。我们需要某种异步流量控制。如果我们做得对，数据应该在不间断地从服务器流向客户端，但只有在客户端读取数据时才会这样。

让我们回顾一下我们的三个协议。这是第一个：

```
C: fetch
S: chunk 1
S: chunk 2
S: chunk 3
....
```

第二个为每个块引入了请求：

```
C: fetch chunk 1
S: send chunk 1
C: fetch chunk 2
S: send chunk 2
C: fetch chunk 3
S: send chunk 3
C: fetch chunk 4
....
```

这里是一个更改后的协议，它解决了性能问题：

```
C: fetch chunk 1
C: fetch chunk 2
C: fetch chunk 3
S: send chunk 1
C: fetch chunk 4
S: send chunk 2
S: send chunk 3
....
```

它看起来可疑地相似。事实上，除了我们在等待每个回复之前发送多个请求之外，它是相同的。这是一种称为"管道化"的技术，它有效，因为我们的 DEALER 和 ROUTER 套接字是完全异步的。

以下是我们文件传输测试台的第三个模型，带有管道化。客户端提前发送大量请求（"信用"），然后每次处理传入的块时，它都会发送一个更多的信用。服务器将永远不会发送比客户端请求的更多的块：

这种调整让我们可以完全控制端到端管道，包括所有网络缓冲区和发送方和接收方的 ZeroMQ 队列。我们确保管道始终充满数据，同时永远不会超过预定义的限制。更重要的是，客户端决定何时向发送方发送"信用"。它可以在接收到块时发送，也可以在完全处理块时发送。这是异步发生的，没有显着的性能成本。

在第三个模型中，我选择了 10 条消息的管道大小（每条消息都是一个块）。这将花费每个客户端最多 2.5MB 的内存。因此，使用 1GB 的内存，我们可以处理至少 400 个客户端。我们可以尝试计算理想的管道大小。发送 1GB 文件大约需要 0.7 秒，每个块大约需要 160 微秒。往返需要 300 微秒，因此管道需要至少 3-5 个块才能保持服务器忙碌。实际上，5 个块的管道仍然会出现性能峰值，可能是因为信用消息有时会被传出数据延迟。所以在 10 个块时，它始终有效。

```bash
$ time ./fileio3
4291 chunks received, 1072741824 bytes

real    0m0.777s
user    0m0.096s
sys     0m1.120s
```

严格测量。你的计算可能很好，但现实往往有自己的观点。

我们制作的显然还不是一个真正的文件传输协议，但它证明了模式，我认为它是最简单的合理设计。对于一个真正的工作协议，我们可能想要添加一些或全部：

* 身份验证和访问控制，即使没有加密：关键不是保护敏感数据，而是捕获像将测试数据发送到生产服务器这样的错误。

* 一个便宜样式的请求，包括文件路径、可选压缩，以及我们从 HTTP 中学到的其他有用的东西（如 If-Modified-Since）。

* 一个便宜样式的响应，至少对于第一个块，提供元数据，如文件大小（以便客户端可以预分配，并避免令人不快的磁盘已满情况）。

* 一次获取一组文件的能力，否则协议对于大量小文件来说变得低效。

* 客户端在完全接收文件时的确认，以恢复客户端意外断开连接时可能丢失的块。

到目前为止，我们的语义一直是"获取"；也就是说，接收者知道（以某种方式）他们需要一个特定的文件，所以他们请求它。文件存在和它们所在位置的知识然后通过带外传递（例如，在 HTML 页面中的链接中的 HTTP）。

"推送"语义怎么样？有两个合理的用例。首先，如果我们采用集中式架构，文件位于主"服务器"上（不是我提倡的，但人们有时喜欢这样），那么允许客户端将文件上传到服务器是非常有用的。其次，它让我们做一种文件的发布 - 订阅，客户端要求某种类型的新文件；当服务器获得这些文件时，它会将它们转发给客户端。

获取语义是同步的，而推送语义是异步的。异步的聊天性较低，因此更快。

更进一步地思考这一点，我们可以看到获取只是发布 - 订阅的一个特例。因此，我们可以得到两个世界的最佳。以下是一般设计：

* 获取此路径
* 这里是信用（重复）

为了使其工作，我们需要更明确地说明我们如何向服务器发送信用。将管道化的"获取块"请求视为信用的可爱技巧是行不通的，因为客户端不再知道哪些文件实际存在、它们有多大等等。

如果客户端说，"我准备好接收 250,000 字节的数据"，这应该同样适用于 250K 字节的 1 个文件，或 2,500 字节的 100 个文件。

这给了我们"基于信用的流量控制"，它有效地消除了对高水位标记的需求，以及内存溢出的任何风险。

## 状态机

软件工程师倾向于将（有限）状态机视为一种中介解释器。也就是说，你采用一种常规语言并将其编译成状态机，然后执行状态机。状态机本身很少对开发人员可见：它是一个内部表示——优化的、压缩的、奇异的。

然而，事实证明，状态机作为协议处理程序的一级建模语言也很有价值，例如，ZeroMQ 客户端和服务器。ZeroMQ 使得设计协议变得相当容易，但我们从未定义过一个编写这些客户端和服务器的良好模式。

协议至少有两个级别：

* 我们如何在网络上表示单个消息。
* 消息如何在对等方之间流动，以及每条消息的重要性。

我们在本章中已经看到了如何生成处理序列化的编解码器。这是一个好的开始。但如果我们把第二项工作留给开发人员，这给了他们很大的解释空间。当我们制作更雄心勃勃的协议（文件传输 + 心跳 + 信用 + 身份验证）时，尝试手工实现客户端和服务器变得越来越不合理。

是的，人们几乎系统地这样做。但成本很高，而且它们是可以避免的。我将解释如何使用状态机建模协议，以及如何从那些模型中生成整洁而可靠的代码。

我使用状态机作为软件构建工具的经验可以追溯到 1985 年，以及我的第一份工作，为应用程序开发人员制作工具。1991 年，我将这些知识转化为一个名为 Libero 的免费软件工具，它从简单的文本模型中吐出可执行的状态机。

关于 Libero 模型的事情是，它是可读的。也就是说，你将程序逻辑描述为命名状态，每个状态接受一组事件，每个状态做一些实际的工作。生成的状态机像老板一样驱动你的应用程序代码。

Libero 在其工作中非常迷人，精通多种语言，并且鉴于状态机的神秘性质，适度受欢迎。我们在几十个大型分布式应用程序中愤怒地使用了 Libero，其中一个最终在 2011 年运行了 20 年后被关闭。状态机驱动的代码构建工作得如此之好，以至于这种方法从未成为软件工程主流的事实令人印象深刻。

因此，在本节中，我将解释 Libero 的模型，并演示如何使用它来生成 ZeroMQ 客户端和服务器。我们将再次使用 GSL，但就像我说的，原则是通用的，你可以使用任何脚本语言将这些代码生成器组合在一起。

作为一个工作示例，让我们看看如何使用 ROUTER 套接字与对等方进行有状态的对话。我们将使用状态机开发服务器（并手工开发客户端）。我们有一个简单的协议，我将称之为"NOM"。

我还没有找到一个快速的方法来解释状态机编程的真正本质。根据我的经验，它总是需要几天的实践。在接触了这个想法三四天后，大脑中会出现一个近乎可听见的"点击！"，因为大脑中的某些东西将所有部分连接在一起。

关于状态机的一个有用的事情是，你可以逐个状态地阅读它们。每个状态都有一个唯一的描述性名称和一个或多个事件，我们可以按任何顺序列出这些事件。对于每个事件，我们执行零个或多个动作，然后我们移动到下一个状态（或保持在同一状态）。

在 ZeroMQ 协议服务器中，我们每个客户端有一个状态机实例。这听起来很复杂，但它不是，正如我们将看到的。

我们将第一个状态描述为有一个有效事件。我们检查用户的凭据，然后到达已验证状态。

已验证状态是我们处理这两个可能事件的地方，通过向客户端发送适当的回复。如果身份验证失败，我们返回到开始状态，客户端可以再次尝试。

当我们成功通过身份验证后，我们到达就绪状态。在这里我们有三个可能的事件：来自客户端的消息，或心跳定时器事件。

关于这个状态机模型，还有一些值得了解的事情：

* 大写的事件是来自客户端消息的//外部事件//。
* 小写的事件是由服务器中的代码产生的//内部事件//。
* "Send SOMETHING"动作是向客户端发送特定回复的简写。
* 在特定状态中未定义的事件会被静默忽略。

现在，这些漂亮图片的原始来源是一个 XML 模型：

```xml
<class name = "nom_server" script = "server_c">

<state name = "start">
    <event name = "OHAI" next = "authenticated">
        <action name = "check credentials" />
    </event>
</state>

<state name = "authenticated">
    <event name = "ok" next = "ready">
        <action name = "send" message ="OHAI-OK" />
    </event>
    <event name = "error" next = "start">
        <action name = "send" message = "WTF" />
    </event>
</state>

<state name = "ready">
    <event name = "ICANHAZ">
        <action name = "send" message = "CHEEZBURGER" />
    </event>
    <event name = "HUGZ">
        <action name = "send" message = "HUGZ-OK" />
    </event>
    <event name = "heartbeat">
        <action name = "send" message = "HUGZ" />
    </event>
</state>
</class>
```

代码生成器在 examples/models/server_c.gsl 中。它是一个相当完整的工具，我稍后会在更重要的工作中使用和扩展它。它生成：

* C 中的服务器类（nom_server.c、nom_server.h），实现整个协议流。
* 一个自测方法，运行在 XML 文件中列出的自测步骤。
* 文档，以图形（漂亮的图片）的形式。

以下是一个简单的启动生成的 NOM 服务器的主程序：

```c
#include "czmq.h"
#include "nom_server.h"

int main (int argc, char *argv [])
{
    printf ("Starting NOM protocol server on port 5670...\n");
    nom_server_t *server = nom_server_new ();
    nom_server_bind (server, "tcp://*:5670");
    nom_server_wait (server);
    nom_server_destroy (&server);
    return 0;
}
```

生成的 nom_server 类是一个相当经典的模型。它在 ROUTER 套接字上接受客户端消息，因此每个请求上的第一帧是客户端的连接标识。服务器管理一组客户端，每个客户端都有状态。当消息到达时，它将这些消息作为事件馈送到状态机。

每个客户端都作为一个对象持有，具有各种属性，包括我们需要表示状态机实例的变量：

```c
event_t next_event;         //  Next event
state_t state;              //  Current state
event_t event;              //  Current event
```

你现在会看到我们正在生成技术上完美的代码，具有我们想要的精确设计和形状。nom_server 类不是手工编写的唯一线索是代码太好了。抱怨代码生成器产生糟糕代码的人已经习惯了糟糕的代码生成器。

这是一些相当优雅的东西：一个单一的源文件，描述了我的服务器状态机，并且还包含了我的动作的原生实现。高级和低级的一个很好的组合，大约比 C 代码小 90%。

顺便说一句，这个简单的小状态机设计只向我们的自定义代码暴露了三个变量：

* self->next_event
* self->request
* self->reply

在 Libero 状态机模型中，还有一些我们在这里没有使用的概念，但我们在编写更大的状态机时将需要这些概念：

* 异常，让我们编写更简洁的状态机。当动作引发异常时，事件的进一步处理停止。
* Defaults 状态，我们可以在其中定义事件的默认处理（对于异常事件特别有用）。

## 使用 SASL 进行身份验证

当我们于 2007 年设计 AMQP 时，我们选择了简单身份验证和安全层（SASL）作为身份验证层，这是我们从 BEEP 协议框架中获取的想法之一。

SASL 乍看之下看起来很复杂，但它实际上很简单，并且非常适合基于 ZeroMQ 的协议。我特别喜欢 SASL 的是它是可扩展的。你可以从匿名访问或纯文本身份验证开始，没有安全性，然后随着时间的推移发展到更安全的机制，而无需更改你的协议。

我现在不打算做一个深入的解释，因为我们稍后会看到 SASL 的实际应用。但我将解释这个原则，这样你已经有所准备了。

在 NOM 协议中，客户端以 OHAI 命令开始，服务器要么接受（"嗨，Joe！"），要么拒绝。这很简单，但不可扩展，因为客户端和服务器必须预先同意他们要进行身份验证的类型。

SASL 引入的天才之处是一个完全抽象和可协商的安全层，在协议级别仍然易于实现。它工作原理如下：

* 客户端连接。
* 服务器挑战客户端，传递它知道的安全"机制"列表。
* 客户端选择它知道的安全机制，并用不透明的数据块回答服务器的挑战。
* 服务器接受客户端选择的安全机制，并将该数据块传递给其自己的安全库。
* 库要么接受客户端的回答，要么服务器再次挑战。

有许多免费的 SASL 库。当我们遇到真正的代码时，我们将只实现两种机制，ANONYMOUS 和 PLAIN，这两种机制不需要任何特殊的库。

为了支持 SASL，我们必须在"开放对等"流程中添加一个可选的挑战/响应步骤。

## 大规模文件发布：FileMQ

让我们将所有这些技术结合到一个文件分发系统中，我将称之为 FileMQ。这将是一个真正的产品，生活在 GitHub 上。我们在这里要做的是 FileMQ 的第一个版本，作为一个培训工具。如果这个概念有效，真正的东西最终可能会得到自己的书。

### 为什么要制作 FileMQ？

为什么要制作文件分发系统？我已经解释了如何通过 ZeroMQ 发送大文件，而且它真的非常简单。但如果你想让消息传递对能够使用 ZeroMQ 的人数多一百万倍，你需要另一种 API。一个我五岁儿子都能理解的 API。一个通用的 API，不需要编程，并且可以与几乎每一个应用程序一起工作。

是的，我说的是文件系统。这是 DropBox 模式：把你的文件扔到某个地方，当网络再次连接时，它们会被神奇地复制到其他地方。

然而，我瞄准的是一个完全分散的架构，它看起来更像 git，不需要任何云服务（尽管我们可以把 FileMQ 放在云端），并且可以进行多播，即，可以同时向多个地方发送文件。

FileMQ 必须是安全的（能够安全），易于嵌入到随机脚本语言中，并且在国内和办公网络上尽可能快。

我想用它来通过 WiFi 将手机中的照片备份到笔记本电脑上。在会议中实时跨 50 台笔记本电脑共享演示幻灯片。在会议中与同事共享文档。在抗议或骚乱期间，将手机中的视频在录制时发送出去。将配置文件同步到 Linux 服务器云中。

一个有远见的想法，不是吗？嗯，想法是廉价的。困难的部分是制作这个，并使其简单。

### 初始设计：API

以下是我对第一个设计的看法。FileMQ 必须是分布式的，这意味着每个节点都可以同时是服务器和客户端。但我不希望协议是对称的，因为那看起来是被迫的。我们有一个从点 A 到点 B 的文件自然流，其中 A 是"服务器"，B 是"客户端"。如果文件反向流动，那么我们有两个流。

因此，我将 FileMQ 构建为两个部分：客户端和服务器。然后，我将这些部分放在一个主应用程序（filemq 工具）中，该应用程序可以同时充当客户端和服务器。这两个部分看起来与 nom_server 非常相似，具有相同类型的 API。

如果我是一个热心的年轻开发人员，渴望在另一种语言中使用 FileMQ，我可能会花一个愉快的周末编写这个公共 API 的绑定，然后将其放在 filemq 项目的子目录中，比如说 bindings/，并发出拉取请求。

### 初始设计：协议

协议的全名是"文件消息队列协议"，或 FILEMQ，大写以区别于软件。

为了开始，我们将协议写成 ABNF 语法。我们的语法从客户端和服务器之间的命令流开始。你应该认识到这些作为我们已经看到的各种技术的组合：

```
filemq-protocol = open-peering *use-peering [ close-peering ]

open-peering    = C:OHAI *( S:ORLY C:YARLY ) ( S:OHAI-OK / error )

use-peering     = C:ICANHAZ ( S:ICANHAZ-OK / error )
                / C:NOM
                / S:CHEEZBURGER
                / C:HUGZ S:HUGZ-OK
                / S:HUGZ C:HUGZ-OK

close-peering   = C:KTHXBAI / S:KTHXBAI

error           = S:SRSLY / S:RTFM
```

以下是服务器可以告诉客户端事情出错的几种方式：

```
;   Server error reply - refused due to access rights
S:SRSLY         = signature %x80 reason

;   Server error reply - client sent an invalid command
S:RTFM          = signature %x81 reason
```

FILEMQ 生活在 ZeroMQ 非协议网站上，并在 IANA（互联网分配号码管理局）注册了一个 TCP 端口，即端口 5670。

### 构建和尝试 FileMQ

FileMQ 栈在 GitHub 上。它像一个经典的 C/C++ 项目一样工作：

```bash
git clone git://github.com/zeromq/filemq.git
cd filemq
./autogen.sh
./configure
make check
```

你想为此使用最新的 CZMQ 主版本。现在尝试运行 track 命令，这是一个使用 FileMQ 跟踪一个目录在另一个目录中的更改的简单工具：

```bash
cd src
./track ./fmqroot/send ./fmqroot/recv
```

并打开两个文件导航器窗口，一个进入 src/fmqroot/send，一个进入 src/fmqroot/recv。将文件拖入发送文件夹，你会看到它们到达接收文件夹。服务器每秒检查一次新文件。删除发送文件夹中的文件，它们也会在接收文件夹中被删除。

我使用 track 来做诸如更新我的 MP3 播放器之类的事情，该播放器作为 USB 驱动器安装。当我在笔记本电脑的音乐文件夹中添加或删除文件时，MP3 播放器上也会发生同样的变化。

FILEMQ 不是一个完整的复制协议，但我们稍后会解决这个问题。

### 内部架构

为了构建 FileMQ，我使用了很多代码生成，可能对于一个教程来说太多了。然而，代码生成器都是可重用的，并且对于我们最终在移动部分中的项目很重要。它们是我们之前看到的集合的演变：

* codec_c.gsl：为给定协议生成消息编解码器。
* server_c.gsl：为协议和状态机生成服务器类。
* client_c.gsl：为协议和状态机生成客户端类。

学习使用 GSL 代码生成的最佳方法是将这些翻译成你选择的语言，并制作你自己的演示协议和栈。你会发现它相当简单。

FileMQ 架构实际上分为两层。有一套通用类来处理块、目录、文件、补丁、SASL 安全性和配置文件。然后，有生成的栈：消息、客户端和服务器。

这些类提供了一个多线程 API，我们已经使用过几次的模型。当你创建一个 API 实例时，这个方法会启动一个后台线程来完成实际工作，即运行服务器或客户端。其他 API 方法然后通过 ZeroMQ 套接字与这个线程对话。

### 公共 API

公共 API 由两个类组成：

* fmq_client：提供客户端 API，具有连接到服务器、配置客户端和订阅路径的方法。
* fmq_server：提供服务器 API，具有绑定到端口、配置服务器和发布路径的方法。

### 设计说明

制作 FileMQ 最困难的部分不是实现协议，而是在内部维护准确的状态。FTP 或 HTTP 服务器本质上是无状态的。但发布/订阅服务器必须维护订阅，至少。

所以我会介绍一些设计方面：

* 客户端通过缺少来自服务器的心跳（HUGZ）来检测服务器是否已死。然后，它通过发送 OHAI 来重新启动其对话。
* 如果客户端停止回复心跳，服务器得出结论客户端已死，并删除客户端的所有状态，包括其订阅。
* 客户端 API 在内存中保存订阅，并在成功连接时重播它们。这意味着调用者可以随时订阅。
* 服务器和客户端使用虚拟路径，非常类似于 HTTP 或 FTP 服务器。你发布一个或多个挂载点，每个挂载点对应服务器上的一个目录。每个这些都映射到某个虚拟路径。
* 客户端可以随时随地重新连接；如果客户端发送 OHAI，这标志着任何先前对话的结束和新对话的开始。

### 配置

我已经构建了几个大型服务器产品，比如 90 年代后期流行的 Xitami Web 服务器，以及 OpenAMQ 消息传递服务器。使配置变得简单和明显是使这些服务器变得有趣的重要组成部分。

我们通常会解决一些问题：

* 使用产品提供默认配置文件。
* 允许用户添加自定义配置文件，这些文件永远不会被覆盖。
* 允许用户从命令行配置。

然后，将这些分层，使命令行设置覆盖自定义设置，自定义设置覆盖默认设置。做到这一点可能是一项艰巨的工作。

对于 FileMQ，我采用了一种更简单的方法：所有配置都是通过 API 完成的。

这是如何启动和配置服务器的方法：

```c
server = fmq_server_new ();
fmq_server_configure (server, "server_test.cfg");
fmq_server_publish (server, "./fmqroot/send", "/");
fmq_server_publish (server, "./fmqroot/logs", "/logs");
fmq_server_bind (server, "tcp://*:5670");
```

我们确实为配置文件使用了特定的格式，即 ZPL，这是一种极简主义的语法，我们几年前开始用于 ZeroMQ"设备"，但它适用于任何服务器。

### 文件稳定性

轮询目录中的更改然后对新文件执行"有趣"的操作是相当常见的。但当一个进程正在写入文件时，其他进程不知道文件何时已完全写入。一个解决方案是添加第二个"指示器"文件，我们在创建第一个文件后创建该文件。

有一个更简洁的方法，即检测文件何时"稳定"，即，没有人再写入它。FileMQ 通过检查文件的修改时间来做到这一点。如果它超过一秒钟，那么文件被认为是稳定的，至少稳定到可以运送给客户端的程度。

### 恢复和后期加入者

就目前而言，FileMQ 还有一个主要问题：它没有办法让客户端从故障中恢复。场景是客户端连接到服务器，开始接收文件，然后由于某种原因断开连接。网络可能太慢，或者中断。客户端可能在笔记本电脑上，该笔记本电脑已关闭，然后恢复。WiFi 可能已断开连接。

在经典的 ZeroMQ 发布 - 订阅模式中，有两个强有力的基本假设，这两个假设在 FileMQ 的现实世界中通常都是错误的。首先，数据过期得非常快，因此要求旧数据没有任何兴趣。其次，网络是稳定的，很少中断。

采用任何 FileMQ 用例，你会看到，如果客户端断开连接并重新连接，那么它应该得到它错过的任何东西。进一步的改进是从部分故障中恢复，就像 HTTP 和 FTP 所做的那样。

一个答案是"持久订阅"，FILEMQ 协议的第一个草案旨在支持这一点，使用服务器可以保留并存储的客户端标识符。因此，如果客户端在故障后重新出现，服务器会知道它尚未收到哪些文件。

有状态服务器制作起来很糟糕，而且难以扩展。我们如何做到这一点？nicer 如果每个客户端连接都独立工作，并携带所有必要的状态。

另一个答案是添加两个概念：重新同步选项和缓存字段（字典）。如果客户端想要恢复，它会设置重新同步选项，并通过缓存字段告诉服务器它已经拥有哪些文件。

尽管我们没有在 FileMQ 中这样做，但服务器可以使用缓存信息来帮助客户端赶上它错过的删除。为此，它必须记录删除，然后在客户端订阅时将此日志与客户端缓存进行比较。

### 测试用例：Track 工具

为了正确测试像 FileMQ 这样的东西，我们需要一个使用实时数据的测试用例。我的系统管理员任务之一是管理音乐播放器上的 MP3 曲目。当我将曲目下载到我的音乐文件夹中时，我想将它们复制到我的播放器上，当我发现让我烦恼的曲目时，我会在音乐文件夹中删除它们，并希望它们也从播放器中消失。

这有点过分强大，适用于强大的文件分发协议。我可以使用 bash 或 Perl 脚本来编写这个，但老实说，FileMQ 中最难的工作是目录比较代码，我想从中受益。

所以我组装了一个名为 track 的简单工具，它调用 FileMQ API。从命令行，这使用两个参数运行；发送和接收目录：

```bash
./track /home/ph/Music /media/3230-6364/MUSIC
```

代码是如何使用 FileMQ API 进行本地文件分发的一个简洁示例。

注意我们如何使用此工具中的物理路径。服务器发布物理路径/home/ph/Music，并将其映射到虚拟路径/。客户端订阅/，并在/media/3230-6364/MUSIC 中接收所有文件。

### 获取官方端口号

我们一直在示例中使用端口 5670 for FILEMQ。与本书中之前的所有示例不同，此端口不是任意的，而是由互联网分配号码管理局（IANA）分配的。

我将非常简要地解释何时以及如何为你的应用程序协议请求注册的端口号。主要原因是为了确保你的应用程序可以在野外运行，而不会与其他协议发生冲突。

如果你打算制作任何重要的公共协议，比如 FILEMQ，你将需要一个 IANA 注册的端口。我将简要解释如何做到这一点：

* 清楚地记录你的协议，因为 IANA 会希望你打算如何使用端口的规范。
* 确定你想要哪些传输协议：UDP、TCP、SCTP 等。使用 ZeroMQ，你通常只需要 TCP。
* 填写 iana.org 上的申请，提供所有必要的信息。
* IANA 将通过电子邮件继续该过程，直到你的申请被接受或拒绝。

请注意，你不会请求特定的端口号；IANA 会为你分配一个。因此，在发布软件之前开始此过程是明智的，而不是之后。
