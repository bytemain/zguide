# 结语

## 来自外界的故事

我请本书的一些贡献者告诉我们他们正在用 ZeroMQ 做什么。以下是他们的故事。

### Rob Gagnon 的故事

"我们使用 ZeroMQ 来帮助聚合我们全球电信服务器网络中每分钟发生的数千个事件，以便我们能够准确地报告和监控需要我们关注的情况。ZeroMQ 不仅使系统的开发变得更加容易，而且比我们在原始设计中计划的开发速度更快、更健壮和容错。

"我们能够轻松地从网络中添加和删除客户端，而不会丢失任何消息。如果我们需要增强系统的服务器部分，我们也可以停止并重新启动它，而不必担心先停止所有客户端。ZeroMQ 的内置缓冲使这一切成为可能。"

### Tom van Leeuwen 的故事

"我正在寻找创建某种服务总线，将各种服务连接在一起。已经有一些产品实现了代理，但它们没有我需要的功能。偶然间，我发现了 ZeroMQ，它太棒了。它非常轻量级、精简、简单且易于理解，因为指南非常完整且读起来很好。我实际上实现了 Titanic 模式和 Majordomo 代理，并做了一些补充（客户端/工作人员身份验证和工作人员发送目录解释他们提供什么以及如何寻址他们）。

"关于 ZeroMQ 的美妙之处在于它是一个库而不是应用程序。你可以随意塑造它，它只是将排队、重新连接、TCP 套接字等无聊的东西放到后台，确保你可以专注于对你重要的事情。我用 Ruby 实现了各种工作人员/客户端和代理，因为这是我们用于开发的主要语言，但也实现了一些 PHP 客户端来从现有的 PHP Web 应用程序连接到总线。我们使用这个服务总线来实现云服务，将各种平台设备连接到暴露自动化功能的服务总线。

"ZeroMQ 非常容易理解，如果你花一天时间学习指南，你就会对它如何工作有很好的了解。我是一个网络工程师，而不是软件开发人员，但设法为我们的自动化需求创建了一个非常好的解决方案！ZeroMQ：非常感谢！"

### Michael Jakl 的故事

"我们使用 ZeroMQ 在我们的分布式处理管道中每天分发数百万个文档。我们从具有各自问题和问题的大型消息队列代理开始。在追求简化架构的过程中，我们选择了 ZeroMQ 来做连接。到目前为止，它对我们的架构如何扩展以及如何轻松更改和移动组件产生了巨大影响。丰富的语言绑定让我们为工作选择合适的工具，而不会牺牲系统中的互操作性。我们没有使用很多套接字（整个应用程序中少于 10 个），但这正是我们需要的，可以将一个巨大的单体应用程序拆分成小的独立部分。

"总的来说，ZeroMQ 让我保持理智，并帮助我的客户保持在预算之内。"

### Vadim Shalts 的故事

"我是 ActForex 公司的团队负责人，该公司开发金融市场软件。由于我们领域的性质，我们需要快速处理大量价格。此外，最大限度地减少处理订单和价格的延迟至关重要。实现高吞吐量是不够的。一切都必须在软实时中处理，每个价格具有可预测的超低延迟。系统由多个交换消息的组件组成。每个价格可能需要很多处理阶段，每个阶段都会增加总延迟。因此，组件之间消息传递的低延迟和可预测延迟成为我们架构的关键因素。

"我们调查了不同的解决方案，以找到适合我们需求的东西。我们尝试了不同的消息代理（RabbitMQ、ActiveMQ Apollo、Kafka），但无法通过其中任何一个实现低延迟和可预测延迟。最后，我们选择了 ZeroMQ 与 ZooKeeper 结合用于服务发现。使用 ZeroMQ 进行复杂的协调需要相对较大的努力和良好的理解，这是由于多线程的自然复杂性。我们发现，像 ZooKeeper 这样的外部代理是服务发现和协调的更好选择，而 ZeroMQ 可以主要用于简单消息传递。ZeroMQ 完美地融入了我们的架构。它使我们能够使用最少的努力实现所需的延迟。它使我们免于消息处理中的瓶颈，并使处理时间非常稳定和可预测。

"我可以明确地推荐 ZeroMQ 用于低延迟很重要的解决方案。"

## 本书是如何诞生的

当我开始写 ZeroMQ 书时，我们仍在 ZeroMQ 社区中争论分支和拉取请求的利弊。今天，值得庆幸的是，这个争论似乎已经解决：我们在 2012 年初为 libzmq 采用的"自由"政策打破了我们对单一主要作者的依赖，并为数十名新贡献者开放了场地。更深刻的是，它让我们转向了一种温和的有机进化模型，这与旧的强制行军模型非常不同。

我之所以有信心这会奏效，是因为我们在指南上的工作已经指明了一年多的道路。确实，文本是我自己的工作，这也许应该是这样。写作不是编程。当我们写作时，我们讲述一个故事，一个人不希望不同的声音讲述一个故事；它感觉很奇怪。

对我来说，这本书真正的长期价值在于示例库：24 种不同语言中约 65,000 行代码。这在一定程度上是为了让更多人能够使用 ZeroMQ。人们已经提到了 Python 和 PHP 示例库——两个最完整的——当他们想告诉别人如何学习 ZeroMQ 时。但它也关乎学习编程语言。

以下是 Tcl 中的代码循环：

```tcl
while {1} {
    # Process all parts of the message
    zmq message message
    frontend recv_msg message
    set more [frontend getsockopt RCVMORE]
    backend send_msg message [expr {$more?"SNDMORE":""}]
    message close
    if {!$more} {
        break ; # Last message part
    }
}
```

以下是 Lua 中的相同循环：

```lua
while true do
    --  Process all parts of the message
    local msg = frontend:recv()
    if (frontend:getopt(zmq.RCVMORE) == 1) then
        backend:send(msg, zmq.SNDMORE)
    else
        backend:send(msg, 0)
        break;      --  Last message part
    end
end
```

这个特定示例（rrbroker）存在于 C#、C++、CL、Clojure、Erlang、F#、Go、Haskell、Haxe、Java、Julia、Lua、Node.js、Perl、PHP、Python、Ruby、Scala、Tcl 中，当然还有 C。这个代码库，所有这些都作为 MIT/X11 许可证下的开源提供，可能构成其他书籍或项目的基础。

但这个翻译集合最深刻说明的是：你选择的语言是一个细节，甚至是一个干扰。ZeroMQ 的力量在于它给你的模式，让你构建，这些超越了语言的来来去去。作为软件和社会架构师，我的目标是构建能够持续几代人的结构。似乎没有必要只瞄准几十年。

## 消除摩擦

我将用我们消除的摩擦来解释我们使用的技术工具链。在本书中，我们讲述一个故事，目标是尽可能便宜和平稳地接触尽可能多的人。

核心想法是将文本和示例托管在 GitHub 上，并让任何人都能轻松贡献。然而，事实证明这比这更复杂。

让我们从分工开始。我是一个好作家，可以快速产生大量不错的文本。但对我来说不可能的是提供其他语言的示例。由于核心 ZeroMQ API 在 C 中，用 C 编写原始示例似乎是合乎逻辑的。此外，C 是一个中立的选择；它也许是唯一不会引发强烈情绪的语言。

如何鼓励人们制作示例的翻译？我们尝试了几种方法，最后最有效的是在文本中的每个示例上提供"选择你的语言"链接，这将人们带到翻译或解释他们如何贡献的页面。它通常的工作方式是，当人们用他们喜欢的语言学习 ZeroMQ 时，他们会贡献少量翻译或修复现有翻译。

与此同时，我注意到一些人相当坚定地翻译//每个单个//示例。这主要是绑定作者，他们意识到示例是鼓励人们使用他们绑定的好方法。为了他们的努力，我扩展了脚本以生成书籍的特定语言版本。我们不是包含 C 代码，而是包含 Python 或 PHP 代码。Lua 和 Haxe 也获得了他们的专用版本。

一旦我们了解了谁在处理什么，我们就知道如何构建工作本身。很明显，为了编写和测试示例，你想要处理的是//源代码//。因此，我们在构建书籍时导入这个源代码，这就是我们制作特定语言版本的方式。

我喜欢用纯文本格式写作。它很快，并且与像 git 这样的源代码控制系统配合得很好。由于我们网站的主要平台是 Wikidot，我使用 Wikidot 非常可读的标记格式写作。

至少在最初的章节中，绘制图表来解释对等方之间的消息流是很重要的。手工制作图表是一项大量的工作，当我们想要以不同格式获得最终输出时，图像转换变成了一件苦差事。我从 Ditaa 开始，它将文本图表转换为 PNG，然后后来切换到 asciitosvg，它生成 SVG 文件，这更好。由于图形是文本图表，嵌入在散文中，使用它们非常容易。

到目前为止，你会意识到我们使用的工具链是高度定制的，尽管它使用了很多外部工具。所有工具都可以在 Ubuntu 上使用，这是一种仁慈，整个自定义工具链都在 zguide 存储库的 bin 子目录中。

让我们走过编辑和发布过程。以下是我们如何制作在线版本：

```bash
bin/buildguide
```

它的工作原理如下：

* 原始文本位于一系列文本文件中（每章一个）。
* 示例位于 examples 子目录中，按语言分类。
* 我们使用自定义 Perl 脚本 mkwikidot 处理文本，生成一组 Wikidot 就绪文件。
* 我们为每种语言执行此操作。
* 我们提取图形，并在每个图形上调用 asciitosvg 和 rasterize 来生成图像文件，我们将这些文件存储在 images 子目录中。
* 我们提取内联列表（未翻译）并将这些列表存储在 listings 子目录中。
* 我们在每个示例和列表上使用 pygmentize 来创建 Wikidot 格式的标记页面。
* 我们使用 Wikidot API 将所有更改的文件上传到在线 wiki。

从头开始执行此操作需要一段时间。因此，我们存储每个图像、列表、示例和文本文件的 SHA1 签名，并且只处理和上传更改，这使得在人们做出新贡献时发布新版本变得容易。

要生成 PDF 和 Epub 格式，我们执行以下操作：

```bash
bin/buildpdfs
```

它的工作原理如下：

* 我们在输入文件上使用自定义 mkdocbook Perl 程序来生成 DocBook 输出。
* 我们将 DocBook 格式推送到 docbook2ps 和 ps2pdf，以每种语言创建干净的 PDF。
* 我们将 DocBook 格式推送到 db2epub，以每种语言创建 Epub 书籍。
* 我们使用 Wikidot API 将 PDF 上传到公共 wiki。

在创建社区项目时，降低"变更延迟"很重要，这是人们看到他们的工作上线或至少看到您接受了他们的拉取请求所需的时间。如果这超过一两天，你通常会失去贡献者的兴趣。

## 许可

我希望人们在他们的工作中重用这段文本：在演示文稿、文章中，甚至其他书籍中。然而，交易是，如果他们混音我的作品，其他人可以混音他们的作品。我想要信用，并且不反对其他人从他们的混音中赚钱。因此，文本是根据 cc-by-sa 许可的。

对于示例，我们从 GPL 开始，但它很快变得明显，这是不可行的。示例的重点是为人们提供可重用的代码片段，以便他们将更广泛地使用 ZeroMQ，如果这些代码是 GPL，这不会发生。我们切换到 MIT/X11，即使对于较大和更复杂的示例，可以想象这些示例可以作为 LGPL 工作。

然而，当我们开始将示例转换为独立项目（如 Majordomo）时，我们使用了 LGPL。再次，可混音性胜过传播。许可证是工具；有意图地使用它们，而不是意识形态。
